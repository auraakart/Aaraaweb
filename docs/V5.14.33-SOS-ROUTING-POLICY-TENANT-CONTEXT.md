# V5.14.33 — SOS routing-policy tenant transactions

**Status:** Merged to `develop` and validated in combined protected CI run #4303
**Target:** `develop` only
**Repository:** `auraakart/Aaraaweb`
**Scope:** Non-production source hardening. No staging/main promotion.

## Finding

The SOS incident/evidence path is being hardened separately. The adjacent routing-policy service still used the root Prisma client for policy reads, responder-candidate reads, responder-membership validation, policy writes and incident-history reads. Although its SQL included explicit `societyId` predicates, these operations did not establish the repository's transaction-local `app.aaraagate_society_id` context.

This slice closes that selected service boundary without claiming that PostgreSQL RLS is enabled.

## Changes

- Run routing-policy list reads through `PrismaService.withTenantContext`.
- Run responder-candidate membership reads through the selected-society transaction.
- Validate the proposed responder's active society membership and `SOS_RESPOND` capability in the same transaction as the policy upsert.
- Keep the policy insert/upsert and all existing severity/deadline/response semantics unchanged.
- Read incident existence and append-only incident events in one selected-society transaction.
- Preserve explicit `societyId` and incident predicates, controller guards, permission checks, feature gating and response shapes.
- Add focused service tests that verify transaction use, permission rejection, atomic membership/write context, validation bounds, incident-history scoping and automation actor rendering.
