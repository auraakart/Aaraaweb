# Aaraagate V5.3 — Runtime Society Branding Engineering Plan

**Baseline:** V5.2.29 is closed on `develop` at `2b49e67ee6fb6db30b684f4dafb64406bc8cde92`.
**Boundary:** Society branding is presentation only, never authorization, an entitlement, a legal issuer, or a commercial partner role. The existing Aaraagate Resident/Guard binaries and default web theme remain the baseline. No staging/main promotion.

## Sequential slices

| Slice | Bounded acceptance and rollback |
|---|---|
| V5.3.1 | Strict versioned presentation JSON contract; additive immutable `SocietyBrandRevision` snapshots with version/digest and draft-to-published transition; authenticated `/context/config` resolves latest published society version inside existing membership/entitlement transaction; missing, corrupt or unpublished revision falls back to exact default. Revert runtime reader if necessary; retain additive records. |
| V5.3.2 | Society-admin-only draft/validate/publish/rollback API reusing `BrandingService`, per-society row serialization, optimistic expected version, approval/canary and conflict tests; no feature override or role mutation. A previous published revision is recovered through a *new* immutable revision. |
| V5.3.3 | Shared Flutter branding theme/config adapter reused in Resident and Guard with exact default tokens, authenticated society switch, stale request rejection, offline fallback and light/dark foreground contrast. No separate code forks or Android identity changes. |
| V5.3.4 | Existing Admin portal editor, CSS custom-property adapter and request-specific metadata; prove accessible default/light/dark, preview not publicly cached and no society-theme bleed. |

These are proposed implementation slices, not all completed or guaranteed to remain exactly six. Each slice requires protected CI on `develop` before the next dependent change.

## V5.3.1 data and behavioral invariants

- `SocietyBrandRevision` is additive; version is unique within one society. Each row has a canonical SHA-256 digest, JSON schema version, creator and optional publication time. A database trigger prevents rewriting snapshot identity/configuration or retracting a publication; future rollback must clone a validated revision under a later version.
- No bootstrap behavior changes. Unauthenticated callers still receive the built-in Aaraagate public presentation only. Independent-home context remains society-less and uses the default without acquiring any society identity.
- Authenticated society context is scoped by active member/auditor authorization and current entitlement read. Only the *selected society's* latest published revision is read in that same tenant transaction. Invalid JSON or digest mismatch falls back to default presentation instead of injecting markup, URLs, CSS, roles, entitlements or feature flags.
- The strict presentation v1 draft fields are `displayName` (trimmed 1–80 display characters) and a complete six-digit `primary` / `primaryDeep` hex color pair. The permitted payload excludes asset URLs until V5.3.5 security validation exists. Accessibility adapters must choose contrast-safe foreground and keep semantic alert/security status colors unchanged.
- Default theme identity, tab navigation, gate notifications, finance payee and receipt legal values remain unchanged. UI adoption is separate and must not be inferred from API support.

## Evidence

- Unit: default bootstrap compatibility, per-society membership/context, integrity fallback, rejected hostile or capability-bearing config, deterministic digest and foreground contrast.
- Native PostgreSQL: two societies, authorized published revision, unpublished draft isolation, irreversible publication, reject post-publish snapshot alteration, foreign society denial and original entitlement behavior.
- Required protected CI: schema/migration, tenant-access register, PostgreSQL acceptance, API lint/typecheck/build, default-brand HTTP smoke, full regression, coverage, Admin/Flutter/security and required merge gates.

**Not in scope:** BrandProfile/partner licensing/domain registry/Android identity (V5.4/V5.5), PostgreSQL RLS activation, production operations, real payment/gate integrations, staging/main promotion. The V5.3 milestone remains IN_PROGRESS until runtime consumers, publish UX and all acceptance gates are complete.


## V5.3.12 — Private society logo asset validation and quarantine

This slice reuses the current society administration permission, active membership, private S3-compatible ObjectStoragePort and ClamAV MediaSafetyScannerPort. It adds an **additive** SocietyBrandLogoAsset table and an authenticated management controller; the brand revision schema and default/public bootstrap remain unchanged.

- POST /branding/manage/logos/uploads: accepts one PNG file descriptor (57 to 524288 bytes), reserves one of four pending slots using a society-row lock, signs a private upload under a server-generated per-society object key, and returns only a short-lived PUT intent and redacted metadata.
- POST /branding/manage/logos/:assetId/confirm: enforces active society management authorization, waits until the signed PUT expires (to prevent replay overwrites), rechecks object size/type/bytes, validates the complete static RGB/RGBA PNG (dimensions, chunks, CRC, bounded decompression), then requires a clean malware scan. Invalid content is rejected. Scanner or object-store unavailability fails closed.
- GET /branding/manage/logos: returns at most 30 rows of authorized metadata, never raw bytes, presigned GET URLs, bucket/storage keys, or partner identity.
- VERIFIED status means **quarantine validation only**. V5.3.13 must implement owner/digest-rechecked binding to immutable brand revisions, authorized asset read, rendering and safe rollback. Neither resident nor guard nor admin will render an uploaded logo in V5.3.12.
- Production environments need private object storage and ClamAV configuration before accepting uploads. No production infra credentials or external provider changes are part of this slice.
- Release gates: schema validation/migration, V5.3.12 PNG parser tests, service permission/quota/object/expiry/scan regression, protected API typecheck/build, tenant-isolation tests, and normal CI. Main/staging untouched.

Rollback is isolated: disable the logo routes and DI bindings without altering earlier brand revisions. Existing SocietyBrandRevision records have no reference to logo assets.


## V5.3.13 — Society Admin private logo review

A society configuration manager can upload a bounded PNG file and request server validation through the existing V5.3.12 private-society object-storage APIs. This intentionally adds **no logo publication**. The Admin editor reuses current session permissions and contains an isolated quarantine panel with no duplicate branding navigation.

- The browser validates the PNG content type and declared size before making a presigned upload request. The server remains the security authority for dimensions, CRC, bytes, malware scanning, society ownership and active membership.
- Presigned object PUT uses no cookies or bearer token, refuses redirects and referrers, and never embeds the object URL in rendered public metadata. Signed object-store endpoint must use HTTPS; local production-like environments must configure CORS for the authorized Admin origin.
- Quarantine metadata parser rejects public URLs, storage keys and unknown asset fields. An item is rendered only as text/status, never as an unverified image.
- Since upload links can be replayed before expiry, confirmation may succeed only after server-enforced URL expiration. Failure or an unavailable scanner leaves the image out of all published revisions.
- Existing approved society-brand versioned editor remains intact. Uploaded logos cannot modify display name/colors/support, tenant authority, finance issuer, gate policy, public bootstrap or native binary appearance.
- CI acceptance includes negative data-parser, unsafe signed URL, empty/oversized/wrong-MIME, no credential propagation, frontend routing and the existing broad Admin contract/test/typecheck/build gates.
- Next *dependent* slice: V5.3.14 — same-society verified logo selection bound into an immutable brand revision, authenticated image read, and consistent Admin/Resident/Guard presentation with defaults and rollback. Keep staged/main release approval separate.

No new backend table, migration or runtime API is introduced here; it reuses the V5.3.12 authoritative contract.


## V5.3.14 — Verified logo reference in immutable society-brand revisions

Only an opaque UUID \`logoAssetId\` is accepted in a society-brand config; external logo URLs, SVG, CSS, storage keys or client-declared verification are never accepted. The canonical digest includes the normalized UUID when present, while existing name/color/support revisions retain their exact historical digests.

The authenticated society-brand editor now reloads **current** society permission and uses the society-row version/publication lock. New drafts that specify a logo must reference a VERIFIED, same-society SocietyBrandLogoAsset with digest and verification timestamp. Publish rechecks the same requirements before the immutable revision's one-time publication transition. Missing, pending, rejected and cross-society logo IDs fail closed without a draft or publication.

The private manager revision-history parser accepts only a canonical UUID; immutable rollback may carry the prior logo asset ID, subject to server validation on new draft/publish. The existing public bootstrap and authenticated Admin/Resident/Guard presentation payload do **not** expose logo IDs, signed URLs or images in this slice. Legacy apps continue to render approved colors/name/support unchanged.

Next V5.3.15 adds authorized image-bytes delivery and opt-in client rendering with session/society rebinding, signed/cached image hygiene, safe defaults and rollback. Any client rendering without that secured delivery layer is explicitly prohibited.

Regression covers digest stability, URL and unsafe ID rejection, same-society VERIFIED lookup at draft and publish, revocation/invalid asset failure, and prior rendering compatibility. CI must regenerate the tenant-access inventory, then pass full API/Flutter/Admin, CodeQL/security and protected merge gates. Stage/main stay untouched.


## V5.3.15 — Authenticated current-published logo bytes, not public URLs

New **GET /context/logo** uses the existing BearerGuard and rejects all society, asset, version and cache query selectors. The API resolves the principal's selected society and active membership under the existing tenant transaction before reading the latest published immutable revision. There is never a free-form asset ID supplied by a caller.

- Published revision digest is validated before its logoAssetId is used; a missing logo or corrupt config responds with 404, so clients preserve the built-in Aaraagate fallback.
- A logo must remain VERIFIED, with a matching society owner, stored SHA-256, expired mutable-upload window, expected private key prefix and fixed PNG type/size; no draft, rejected, unverified or foreign-society asset is served.
- After scoped DB authorization, the existing private object-storage adapter returns at most 512 KiB. The API independently rechecks MIME, exact byte count, PNG chunks/CRC/raster bounds and SHA-256 against the originally verified bytes. Modified or unavailable objects fail closed.
- Response is PNG bytes only using StreamableFile and explicit no-cache/no-store, nosniff, authorization vary and restrictive CSP headers. No signed GET, arbitrary external URL, bucket key or public CDN publishing.
- No changes to public bootstrap, authenticated /context/config schema, native mobile identity, roles, payments, gate operations or partner access.
- API unit regressions cover unauthorized/independent-home, revoked membership, missing published revision, digest tampering, cross-society ownership, pending files, unexpired upload, MIME/object-key spoof and changed bytes.
- Follow-on V5.3.16: render this authenticated endpoint in the existing Admin, Resident and Guard design systems with session-safe cancellation and default fallbacks. UI must not cache content across society switches.

This is deliberately a separate secure-delivery slice so a client-side image cannot accidentally bypass tenant and publication controls. No staging/main promotion or production credentials.


## V5.3.16 — Admin verified-logo revision selection and published-image preview

This slice reuses the existing society branding editor, logo quarantine panel, and authenticated PNG endpoint from V5.3.15; no second branding system or backend API is added.

- A VERIFIED private logo can be selected by an authenticated society manager using only the opaque asset ID from the existing branding management logo list. PENDING/REJECTED, guessed, URL-shaped and foreign IDs cannot be selected in the client contract. Server authorization and digest checks remain authoritative at draft and publication.
- The selected ID is included in the existing immutable brand draft payload alongside the display name, palette and support contacts. Existing version conflict handling, immutable published revisions and safe restore remain unchanged.
- Admin previews the current published image only through the bearer-authenticated GET /context/logo API, with omitted cookies, disabled redirects/referrer/cache and no permanent asset URL. Short-lived browser blob URLs are revoked on revision/session changes.
- A missing/rejected image uses the built-in Aaraagate fallback without preventing gate, finance, sign-in or branding workflows. Unpublished drafts are still shown as text/palette previews, never as raw quarantined images.
- Full Admin lint/typecheck/build plus focused V5.3.13 and V5.3.16 negative/UI-contract tests are required. Native Android identity and Resident/Guard image rendering remain separate.

Next dependent V5.3.17: reuse the shared authenticated society presentation lifecycle for Resident and Guard logo byte fetching; guarantee no late response from prior login/society, no persistent cross-tenant cache, and built-in default fallback. Full V5.3 closure requires cross-society, accessibility and rollback evidence.


## V5.3.17 — Resident/Guard in-memory logo presentation

Both Flutter apps reuse existing authenticated society-branding lifecycle and the V5.3.15 server endpoint. A shared, dependency-free Dart fetcher only requests GET /api/v1/context/logo using the current session's bearer token. It rejects redirects, unexpected MIME, oversized/truncated responses and malformed PNG headers; the backend remains authoritative for full PNG CRC, signed upload expiry, SHA-256, tenant membership and immutable published-revision selection.

Optional fetchLogo injection into ResidentBrandingController and GuardBrandingController uses the **same** society/session/credential generation as theme updates. It clears all logo bytes synchronously at logout, credential rotation or society switch, rejects late prior-society requests, keeps bytes in memory only, and shows no logo for independent-home/demo/signed-out contexts. Foreground resume resolves the published theme and image without affecting gate operations, finance or offline queues.

Resident Home and signed-in Guard Operations display the currently authorized PNG via Image.memory with a local icon fallback on decoding error. The app title, installed application icon, native package identity, dark/light tokens, notifications and security rules remain unchanged.

Release verification: targeted Resident/Guard lifecycle regressions, PNG bounding contract, Flutter analyzer and existing risk-weighted tests. No new backend schema, API module, service, cloud assets, outbound image URL, credential persistence, permission or entitlement changes. Staging and main require separate release approval.


## V5.3.18 — Bound mobile logo transport and protect bearer tokens

Review of the merged V5.3.17 shared mobile logo client identified that logo bytes were scoped correctly in memory, but its HTTP transport accepted unencrypted remote origins and used per-chunk idle timeouts instead of a total read deadline. This slice corrects both without rewriting Resident/Guard branding.

- HTTPS is mandatory for nonlocal society logo requests. Plain HTTP is accepted only for localhost, 127.0.0.1, IPv6 loopback and the standard Android emulator bridge `10.0.2.2`. User-info, fragments, query selectors and unexpected routes remain rejected before network I/O or bearer-header attachment.
- The fetcher requests identity encoding to avoid unexpected transformed body lengths, then applies an absolute timeout to the whole PNG read (not a resettable stream idle timeout). It rejects mismatched Content-Length, truncated or oversized data and retains existing MIME, signature, dimension and status checks.
- Resident and Guard share the same validated fetch helper and each has negative regression coverage for remote HTTP, credentials embedded in URLs and arbitrary query/path manipulation. Both preserve immediate logout/society-switch memory clearing and default-logo fallback.
- Full security remains server-authoritative: authenticated currently published revision, tenant-bound live membership, verified object metadata, PNG parse and stored SHA-256. No new image store, API, package dependency, native identity, data migration, productionization, staging or main change.
- CI release conditions: targeted Flutter lifecycle regressions, static analysis for both apps, existing accessibility/behavior tests, API and Admin validations, dependency security, and protected develop merge.
- Follow-on V5.3.19 should focus on final logo rollback/accessibility evidence and any still-open nonproduction branding contract gaps. Do not start partner-specific app cloning or distributions merely to close this milestone.


## V5.3.18 — Secure mobile bearer delivery and bounded image reads

The shared dependency-free Dart logo fetcher accepts HTTPS remote published-logo endpoints, with explicit local loopback/Android-emulator HTTP exceptions for development. It rejects credentials, query/fragment injection, alternate API paths and remote cleartext addresses *before* creating any HTTP client/request or attaching a bearer token. Requests disable redirects, cache and content compression. The complete response body must arrive within a total eight-second deadline and must fit the 512 KiB bound; mismatched declared lengths, unexpected MIME and invalid PNG headers fall back to the built-in branding without affecting resident/guard operations. Full PNG integrity, society ownership and publication authority remain server-side.

CI evidence: Resident and Guard URL-denial/allowlist tests and all protected API/Admin/Flutter and security gates passed in [PR #1260](https://github.com/auraakart/Aaraaweb/pull/1260), merged as `a7cd59749dd0cf35f022d258ae904ae47887ddc5`. Local development exceptions are not production transport recommendations.

## V5.3.19 — Accessible society-logo labels and immutable publication-rollback parity

Resident Home and Guard Operations continue consuming only the current session-scoped, authorized in-memory bytes. When a published PNG is available, each existing screen uses one descriptive image semantics node identified with the validated current society display name. Inner image/text semantics are excluded to avoid duplicate screen-reader announcements. Resident Home's visible name expands and truncates safely in compact layouts instead of using a fixed generic label. All existing guard controls, resident navigation and fallback icons are preserved. No new widget system, backend API, role, database migration or native binary is introduced.

Resident and Guard lifecycle regressions simulate original revision v1, a newly published v2 with a different image, and a **new immutable v3** restoring the original look and logo. Image bytes are cleared on each verified revision change before the next authorized response and again on logout. Existing late-response/cross-society/credential-rotation regressions remain required. Admin continues using the V5.3.8 server-authorized draft/publish restoration, including verified-logo owner checks from V5.3.14: a historical revision is never mutated, and an interrupted two-request restore may leave an unpublished draft for inspection.

Protected acceptance: compile and test both Flutter apps; run existing logo authorization/rollback, Admin permission/restore tests, accessibility semantics regression, tenant-isolation checks and complete CI gates. No staging/main promotion or real production integration is included; V5.3 closure remains conditional on all evidence and gaps.
