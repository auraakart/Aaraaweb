# V5.6.20 — Historical opening-balance journal provenance hardening

Scope: nonproduction engineering, `develop`-only after existing required protected GitHub CI gates.

## Old crash window and trust boundary

The earlier two-transaction migration design could leave a POSTED `OPENING_BALANCE` journal while the owning migration batch was still READY and its rows unlinked. After #1390, new postings and batch linkage are atomic, and #1397/#1398/#1400 exercise historical adoption, concurrent replay, cross-society rejection, hash mismatch and closed period transitions.

A matching externally stored canonical-content digest alone is insufficient immutable accounting audit evidence. The READY-batch historical replay path now checks:

- The existing posted journal ID, society ID, opening-balance source identity and non-reversed status;
- `createdByUserId` and `postedByUserId` **both equal original `MigrationBatch.actorUserId`** (which need not equal the person requesting recovery now);
- The resolved accounting period, entry number, entry date, description, INR currency and original posted time;
- The journal has precisely the batch's number of lines, and its actual persisted journal-line multiset (account/fund/unit/description/debit/credit) equals the canonical migration-derived input with `EXCEPT ALL` multiplicity semantics. Null dimensions are preserved.
- Conflict raises a specific audit-provenance exception *inside the same transaction*, leaving the READY batch and posted journal untouched.

The existing `OpeningBalancesService.applyWithinTransaction` public/API idempotency contract and normal new-post path remain unchanged. No DB migration or new provider. Real disposable PostgreSQL regression uses another actor and asserts no linkage or duplication after a hash-identical but unauthorized historical post.
