# V5.6.7 — Atomic opening-balance migration rollback (nonproduction)

**Baseline:** `develop` `fab07282e81552625b6efa520e07c1159aff18b7`, after protected V5.6.6 (#1385) green/merged. Scope excludes productionization, partner builds, external providers, and promotion outside `develop`.

## Failure mode and correction

Previously, `MigrationOpeningBalanceCommitService.rollback()` first verified a COMMITTED batch and valid journal evidence, then called `AccountingService.reverseJournal()` in its **own committed transaction**, and only subsequently started a **second transaction** for migration row and batch rollback timestamps. A failed batch state update or crash between transactions could leave the journal REVERSED while migration batch remained COMMITTED. The legacy recovery path deliberately allowed completing a pre-existing reversed journal on retry, but this was not atomic.

The new implementation obtains the **batch advisory lock and database row lock before making decisions**, validates the actual rows after locking, locks the referenced journal row, and performs any journal reversal plus MigrationBatchRow / MigrationBatch status updates **within one Prisma interactive transaction**. On callback rejection, the database discards both the accounting reversal and batch state changes. It returns an already-ROLLED_BACK batch idempotently, and keeps the old REVERSED-journal catch-up path for historical partial reversals.

`AccountingService.reverseJournal()` retains its existing standalone API, exception translation and own transaction. The newly factored `reverseJournalWithinTransaction(tx, ...)` uses a caller-provided Prisma transaction with precisely the same ledger reversal SQL, row locking and accounting-period validation; it does **not** open a second transaction. No controller API changes or permissions broadened.

The reversal date now resolves from the same transaction context. The payment/owner/tenant business rules, tenant scoping, accounting entries and reporting queries are unchanged.

## Risk-weighted test evidence

`migration-opening-balance-commit.service.spec.ts` covers:

- malformed/incomplete or invalid journal evidence and split-target rows fail before reverseJournal;
- READY migration batches cannot roll back; already rolled-back batches are no-ops;
- unavailable open accounting period stops journal reversal;
- the exact **same transaction object** flows through journal reversal and subsequent row/batch updates, with sequencing assertions;
- failed batch-state update propagates from the enclosing transaction callback;
- a previously reversed journal follows the bounded historical catch-up path without a second reversal.

These are interaction-level assertions with a mocked transaction. Full protected API validation will also test the existing migrated-PostgreSQL workflows, but this slice does **not** invent an external restore rehearsal or claim that the mock proves physical crash durability. The correctness of PostgreSQL interactive transaction commit/rollback is a dependency of this implementation, to be verified through a future operational disaster-recovery rehearsal.

## Explicit remaining gap

**Opening-balance *commit* remains separate:** `OpeningBalancesService.apply()` posts the initial journal in one transaction, before `MigrationOpeningBalanceCommitService.commit()` records batch linkage in another. Repairing its failure/replay semantics is a follow-up, not part of rollback atomicity and should not be smuggled into this slice.
