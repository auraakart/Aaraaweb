# V5.6.3 — actual API notification isolation regression (nonproduction)

**Baseline**: `develop` `2761aaa84d6d3d64df41ecf98bc624d139616c09`, following V5.6.2 PR #1381 (all protected checks passed). V5.6 remains PLANNED; these are supplementary risk-weighted API tests, not V5.6 release/UAT closure.

## Why this work

The existing `notification-realtime.service.spec.ts` covers successful targeted resident delivery, occupant notifications, one-society gate updates and successful invoice-unit enrichment. Existing migrated-PostgreSQL `payment-integrity.postgres.spec.ts` independently covers occupant vs nonresident owner routing, billing owner/tenant visibility and cross-society payer access.

The additional missing regression concern is **same global user in two society contexts** (which may belong to different commercial partners), and **an unresolvable/foreign-society invoice**. A shared identity must not cause SSE streams to mix or bypass the society-scoped invoice lookup.

## Executable cases

`services/api/src/notifications/v5.6.3-cross-society-realtime.regression.spec.ts` adds five tests exercising the real `NotificationRealtimeService` implementation:

1. Two resident streams for the **same user ID in different societies** remain isolated, including when one subscriber disconnects.
2. A gate decision stream for one society never reaches the other society's stream, even for the same user.
3. An occupant approval event calls the currently scoped recipient resolver with society + unit and does not deliver to a different society; no nonresident owner is synthesized.
4. If an invoice is absent in the event's society, the dispatch path drops the maintenance notification **before** SSE or push. This checks the exact society-scoped Prisma lookup contract.
5. A database lookup error propagates and does not produce a partial maintenance push or SSE notification.

Tests use isolated fake push, recipient and Prisma adapters to assert **observable behavior of the real NestJS service**. They do not claim migrated-PostgreSQL tenant/RLS isolation, authenticated SSE controller authorization, actual FCM delivery, live partner acceptance or device installation. Those remain covered by existing separate integration suites and the unexecuted end-to-end V5.6 acceptance plan. In particular, these tests do not establish a partner-level authorization principal; they verify society-scoped realtime fanout, a necessary lower-level boundary.

## Validation and safety gates

Focused: `pnpm --dir services/api exec vitest run src/notifications/v5.6.3-cross-society-realtime.regression.spec.ts` with repository dependencies installed. Then required protected API/Admin/Flutter/security GitHub checks decide the `develop` merge. No API/runtime edits, Prisma migration, Android build or new CI workflow, no extra full-regression rerun requested, and no `staging` or `main` promotion.

The V5.6.2 matrix continues to mark all 15 **composite acceptance scenarios** `NOT_EXECUTED`: these five narrow mocked-adapter cases alone cannot satisfy the trusted TEST DB, external runner, device and independent ingress evidence prerequisites. V5.4 and V5.5 remain IN_PROGRESS, V5.6 remains PLANNED; independently operated runner/partner build acceptance remains issue #1380.
