# V5.5.3 — Monotonic Android TEST versionCode reservations

Baseline: `develop` at `d720e26c06be2c18897eabe146d2d2e769c17c38` following V5.5.2 (#1293, protected CI #38541594633 successful).
The current slice is strictly a persistent TEST version allocator / immutable reservation ledger, not a build dispatcher.

## Reused authority
V5.4.20 commercial grants, owned-society operator checks, current opt-in and initial distribution approval remain authoritative. V5.5.2's latest independently approved immutable revision binds identity and signer fingerprint. `PartnerAndroidBuildReservationService.reserve` runs within the existing `withActiveAllocation` transaction and locks the immutable distribution proposal row before allocating a version. No new partner membership, operational rights, subscription resolver or API audience is added.

## New immutable record
`PartnerAndroidBuildReservation` records distribution, exact latest reviewed revision, actor, idempotency key, review digest, monotonically allocated Android `versionCode` (1 through 2,100,000,000) and creation time. `proposalId+versionCode` and `proposalId+idempotencyKey` are unique. Direct PostgreSQL INSERT triggers independently recheck current licensing and approval, latest review, tenant and app identity, and require the next sequence under a proposal row lock. UPDATE/DELETE are rejected, so cancelled or failed jobs cannot free a consumed code.

## Scoped API and return semantics
`POST /api/v1/licensing/societies/:societyId/distributions/:proposalId/android-build-reservations`: BearerGuard + SUPER_ADMIN + no-store. Requires existing licensing context, `revisionId`, exact `expectedDigest` and a UUID idempotency key. Same actor/same current revision/same key returns the original reservation; changed payload/actor, unreviewed or superseded revision, revoked distribution, ownership/license drift and exhausted version range fail closed.

Returned fields are deliberately limited to job/reservation identifiers, versionCode, approved-revision digest and `{status:'RESERVED_TEST_ONLY',testOnly:true,dispatchAllowed:false}`. There is **no** CI/workflow dispatch, executable command, callback URL, signing key, artifact, app store publication or branch mutation. The default Resident demo and its app identity are unchanged. The legacy default identity must be verified against actual binaries before separate update continuity is claimed.

## Verification and next step
Targeted unit tests cover initial/monotonic code, idempotent replay, stale scope, digest drift, revoked authority, exhaustion and dispatch refusal. A native PostgreSQL fixture verifies replay, distinct sequence, skipped/reused-code denial, append-only history and revocation. Full required CI (including PostgreSQL migrations/API/Admin/Flutter and security) is the merge gate.

**Still required in a later trusted builder:** actual source/lock digest, published brand and sanitized PNG bytes, signer mapping, app-link verification, Firebase mapping, reliable test signing, artifact identity/version/signature checks, immutable provenance and authenticated reauthorization at **both** dispatch and completion. No source of client-provided snapshot data can bypass these gates. A reservation by itself is not evidence an APK or AAB exists.

Rollback disables new reservation requests but retains immutable rows and spent version codes; never delete history or reassign a code. No staging/main promotion.
