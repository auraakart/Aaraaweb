# V5.4.25 — Validate ingress redirects as browsers interpret them

Baseline: `develop` `633ee0e48fc883340b9eb24f22b7502b6fc7980e`.

The existing V5.4.24 checker accepted any Location starting with a single slash.
For example, `/\other.qa.partner.in/` and a slash followed by a tab and another
slash passed this prefix check, yet WHATWG URL parsing resolves both to a foreign
origin. The checker never follows redirects, but could incorrectly report that
an unsafe ingress response passed its redirect acceptance criterion.

The checker now rejects backslashes, ASCII whitespace/control characters and
DEL; retains its root-relative or exact approved HTTPS URL requirement; and
parses the target with `URL` against the approved origin. The resulting origin
must match, with no credentials. Safe same-host redirects remain supported.

The same response validation previously treated word-boundary substrings as
header tokens: `Vary: X-Host` and `Cache-Control: x-no-store` or
`no-store="ignored"` satisfied the checks. Require exact comma-delimited,
case-insensitive `Host` and `no-store` tokens instead.

The existing mandatory loopback TLS 1.3 suite reproduces the old redirect failure
before the fix, then checks foreign redirects, nondefault ports, userinfo,
HTTP downgrade, whitespace and misleading headers. It accepts approved relative
and absolute HTTPS destinations, verifies rejection stops at the first response,
and keeps all external acceptance flags false. No remote network call is made.
The existing `check-v4.79.1.7` gate already runs this suite; no CI scope changes.
