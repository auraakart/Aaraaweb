# V5.6.6 — Fail-closed opening-balance rollback evidence

**Baseline:** `develop` at `ac5826029d915678285074bba1f2ce44e0c421ae`, after V5.6.5 (#1384) merged with protected checks.

## Defect and correction

`MigrationOpeningBalanceCommitService.rollback()` already required `COMMITTED` batch status, a single target journal ID and a `POSTED`/`REVERSED` journal. However, its pre-reversal check accepted **an incomplete subset of stored batch rows**, provided the remaining rows referenced the same journal. It also did not reject a row whose `valid` flag was false. An inconsistent batch could therefore trigger a financial journal reversal before all original migration evidence was verified.

The rollback preflight now requires exactly `batch.totalRows` rows, each still `valid` and linked to a journal, and exactly one distinct journal ID. An empty batch, deleted/missing row, invalid row, missing target or conflicting target journal fails closed **before** any journal lookup, accounting reversal or migration-batch state mutation. The existing error type and response text are preserved. No change to a correctly evidenced opening-balance rollback.

Two adversarial tests in `migration-opening-balance-commit.service.spec.ts` cover (1) one of two committed migration rows missing and (2) one of two rows flagged invalid. Each asserts `ConflictException` and no accounting reversal / database update transaction. The previously present closed-accounting-period test continues to run.

## Boundaries and follow-up

This is a narrow nonproduction correctness fix, **not** a completed rollback drill or live PostgreSQL recovery claim. The service still performs journal operations and batch evidence transitions in separate transactions; a crash/transaction failure between those operations requires its own separate design review and integration-test evidence. We have deliberately not rewritten the accounting transaction model in this slice.

Run `pnpm --dir services/api exec vitest run src/migration/migration-opening-balance-commit.service.spec.ts` and rely on required protected PR gates before merging into `develop`. No productionization, external runner dispatch, Android partner builds, migrations, `staging` or `main` changes. V5.6 remains PLANNED pending independent TEST acceptance in issue #1380.
