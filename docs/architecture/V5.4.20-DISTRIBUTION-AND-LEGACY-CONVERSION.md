# V5.4.20 distribution approval and V5.1.2 legacy subscription conversion

Baseline: develop `0e88378725f7a40cf467c78cbe7c2e2c8afdbb3c`, after V5.4.19 PR #1289. Implemented in the existing EntitlementsModule and commercial approval ledger. Protected acceptance is pending; no production or staging/main promotion.

## Distribution test-input controls

The selected-society platform operator proposes an immutable TEST identity record. It fixes applicationId/namespace, Resident or Guard role, label, source commit SHA, config digest, test signing-profile reference and explicitly allowlisted HTTPS API origin. Unknown fields, secret fields, mutable refs, default/reserved identities, unsafe labels and production signing profiles are rejected. `AARAGATE_TEST_BUILD_API_ORIGINS` defaults to an empty list, so proposals fail closed without test operator configuration. No pricing, signing key or shell command is accepted.

An independent current SUPER_ADMIN in the same society approves the exact SHA-256 manifest digest and records a reason. Both actors require current society memberships. The active allocation helper rechecks partner ownership/history, immutable grant version, approval/revocation, active period, latest opt-in and exact current legacy tier/overrides/features inside the existing locked transaction. Receipt replays and approved-input reads undergo the same checks. Society/partner/role selection supplied by a client is never authority.

PostgreSQL locks the society then grant/partner. Grant serialization enforces `maximumDistributions` across competing approvals. Revoked identities remain globally reserved; capacity is released through an append-only revocation, with current society operator authority even after licensing expiry, opt-out or transfer. Stale allocations conservatively retain capacity until explicit distribution revocation. Unique request keys support exact retries, not changed actor or payload. Direct database inserts also check current context, maker/checker separation and capacity; records reject UPDATE/DELETE.

Routes under `/api/v1/licensing/societies/:societyId`:

- POST `distributions` — propose immutable test inputs.
- POST `distributions/:proposalId/approvals` — approve exact digest independently.
- POST `distributions/:proposalId/approved-input` — reauthorized read, no-store.
- POST `distributions/:proposalId/revocations` — append-only withdrawal of approval.

All routes use existing BearerGuard/RolesGuard and SUPER_ADMIN scope. A commercial partner role does not gain operational rights. No app audience, host session, push route or build job is created. `APPROVED_TEST_INPUT` is not a production distribution or a complete V5.5 build manifest: build generation must independently resolve/validate source/config/assets, API/Firebase/app-link mappings, signing identity and provenance, and revalidate approval at dispatch and completion before producing an artifact. Approving a digest does not prove the referenced commit/config exists or authorize arbitrary API origins.

## Explicit grandfathered subscription conversion

POST `legacy-subscriptions/conversions` uses the same current platform/society allocation boundary. It creates a single immutable `SocietyLegacySubscription` for the allocation, referencing the historical compatibility row and preserving source migration, raw tier, raw overrides and effective features. Both the current opt-in snapshot and the historical snapshot must match current legacy rights exactly, including unknown override keys. A missing historical row, drift, withdrawn consent, foreign/stale allocation, revoked license, changed actor/key or expired authority fails closed before replay or write. New post-cutover societies lacking historical evidence use the existing licensing flow rather than this historical conversion.

This is an additive commercial representation of grandfathered rights, not an operational feature cutover. `EntitlementService.current`, Society.productTier/featureOverrides and gate/SOS behavior remain authoritative, including after commercial withdrawal/expiry. No pricing, billing period policy, renewal, automatic downgrade or feature removal is invented. Society maintenance invoices, payments, balances and residents are not read or written by conversion. No live society is converted automatically; the endpoint requires explicit existing licensed opt-in and platform action.

Database insert triggers validate same-society allocation, latest consent, baseline/current parity and actor authority. FKs and unique constraints prevent orphan/duplicate conversions; immutability preserves the historical record. Any changed legacy rights require a separately reviewed reconciliation policy, not edits to migration snapshots.

## Acceptance and rollback

Four new native PostgreSQL cases cover independent approvals/replay/withdrawal, serialized capacity and raw self-approval denial, immutable conversion/forged snapshots, and foreign/suspended scope. Canonical CI must deploy all migrations and run these tests before merge. This document does not claim database or protected acceptance before that run succeeds.

Rollback: stop new proposal/approval/conversion requests; revert application readers/writers while retaining additive tables, constraints and append-only history. Legacy entitlement resolution is unchanged. Revoke test distribution approvals before enabling any future build consumer; never drop rows to release identities/capacity. No signed artifacts, Android generation, external provider provisioning or deployed rollback drill in these slices.
