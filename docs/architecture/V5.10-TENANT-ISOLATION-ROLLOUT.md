# V5.10 tenant isolation rollout

Status: read-only catalog preflight and rollout sequence implemented; database policy activation and hosted acceptance remain open under issue #212. No application permission is removed or replaced. `withTenantContext` remains transaction-local context, not an enforced policy.

## Read-only operator preflight

Run `pnpm check:tenant-isolation` with the deployment's **actual runtime-role** `DATABASE_URL`, in a controlled environment. It reads catalog metadata in a read-only transaction with bounded statement/transaction timeouts; it does not modify data, grants, roles or policies. Do not publish the URL or credentials.

The command rejects reachable superuser/BYPASSRLS roles, missing tenant tables, disabled/unforced RLS, missing policies and reachable owner roles. Required direct/hybrid society tables come from the current generated inventory; no hand-maintained short allowlist can silently omit a new table. Output contains table names and gap codes, not database credentials or connection error details. A zero exit status means **catalog prerequisites only**, never isolation certification. Existing development/CI owner-role databases are expected to fail the inspection.

Parent-derived tables without `societyId`, global identity/provider/partner data, external stores and policy expressions still require semantic review. Policy presence is not policy correctness. This preflight deliberately has no environment switch that marks an unprotected database accepted.

## Activation sequence and compatibility

| Batch | Surfaces | Required work before activation |
| --- | --- | --- |
| 1 | Maintenance invoices, payments, receipts and reconciliation | Convert all HTTP, webhook/global order resolution and retry paths to explicitly authorized transaction scope; preserve locking and idempotency namespaces |
| 2 | Privacy requests, evidence, documents and signed file access | Same-society parent/child validation; self/platform exception matrix; retention and storage worker authority |
| 3 | Household, gate, helpdesk, amenities and operational jobs | All scoped reads/writes use transaction client; global jobs enumerate authorized scopes then operate within them |
| 4 | Identity, partner/global and parent-derived relationships | Explicit role/view/function exceptions and parent joins; never infer operational access from branding/commercial ownership |

For each batch: review USING/WITH CHECK expressions and runtime-role grants; test absent and wrong context, reads and inserts/updates/deletes, parent substitution, role inheritance/SET ROLE, pooled reuse, commit/rollback and parallel requests. Run existing owner/tenant/provider/partner and finance regressions against the exact policy-enabled candidate. Check migrations and rollback using production-like non-owner credentials. Database constraints remain in force throughout.

Do not add a blanket RLS migration before every affected call path is converted. Owner/admin access must use a separate narrowly authorized operational path; runtime application credentials must not own tables or inherit a bypass role. Keep scheduler/platform exception rights narrow and audited. Never give a public callback generic tenant-bypass credentials.

Rollback must preserve application authorization and stop writes if policy/data integrity is uncertain. Disabling protections is not an automatic recovery action. Retain default Aaraagate identity, legacy entitlements and historical financial records.

## Remaining decision and evidence

Production-like runtime-role provisioning, staged policy activation, semantic negative tests and independent security approval remain required. No alternative control has been accepted by this repository change. This work closes the missing inspection tooling and concrete rollout plan; it does not close H03's database enforcement or issue #212.
