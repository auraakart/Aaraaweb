# V5.4.17 — Persisted direct-host test session boundary

This slice adds an immutable nullable Session originHost, hostClaimId and hostClaimVersion. Existing STANDARD and unbound PARTNER sessions keep their current behavior. No old session is upgraded to a host-bound session. Database CHECK and FK constraints reject partial or non-PARTNER bindings; a trigger prevents adding, removing or changing the binding after issuance. Normal refresh-token rotation and revocation remain permitted.

`POST /auth/partner/host/otp/verify` reuses existing one-time OTP verification and account authority. Session issuance derives the partner from an exact current VERIFIED domain claim, rather than any body-supplied partner ID. It requires current membership in that exact partner, current unrevoked independent license approval, matching license version and domain capacity. Pending invitations alone do not authorize host sessions.

The adapter requires NODE_ENV=test/development, AARAGATE_ENABLE_TEST_HOST_SESSIONS=true and a nonempty bounded AARAGATE_PLATFORM_HOSTNAMES JSON array. Production is unconditionally disabled. Only raw Host is used. Forwarded and X-Forwarded-Host are rejected; no proxy trust is introduced. Invalid/reserved hostnames fail closed through the shared hostname contract. Mutations require exact HTTPS Origin. GET/HEAD navigation may omit Origin; supplied Origin must match, and a supplied Sec-Fetch-Site must be same-origin or none.

Bearer and refresh revalidate hostname, claim ID/version, verification expiry, active partner, exact active membership and current licensed domain capacity. Revocation, challenge reissue or changed claim version invalidates old host sessions. Refresh cannot strip or change the immutable binding. PartnerBearerGuard restricts bound principals to routes with the exact server-derived partnerId parameter. Global workspace discovery and invitation inbox are denied for these sessions and remain available on the existing platform portal. General BearerGuard continues to reject all PARTNER sessions.

## Validation and boundaries

Behavioral regressions cover host/proxy/origin spoofing, navigation policy, disabled/production modes, reservation configuration, exact partner membership, license capacity, claim withdrawal/version changes, refresh rotation and foreign/unscoped route denial. A native PostgreSQL regression checks legacy compatibility, CHECK/FK constraints, immutable binding and permitted rotation/revocation. Protected CI must execute the native case and all required gates before develop merge. Local validation results belong in the PR.

This is an API test adapter and session persistence slice, not a complete multi-host portal. No Next.js SSR routing, cookies, public-domain activation, trusted proxy, production DNS/TLS, Android distribution or staging/main promotion is included. Future SSR/BFF work must preserve server-origin binding, no-store/private responses, host-only cookies and exact Origin mutation checks without copying tokens between hosts.

## Rollback

Keep the additive columns, FK and immutable history. Disable the test flag and revoke all sessions with nonnull hostClaimId before deploying a previous application revision: older partner guards do not enforce host binding. Merely disabling the flag does not make rollback to older code safe. Revoke through the existing session revocation path; never clear binding columns. Legacy unbound sessions and gate/SOS behavior are unchanged.
