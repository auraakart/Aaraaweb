# V5.6.10 — Atomic opening-balance migration commit

Baseline: `develop` `3265334ce63590b98d90ca111743b222a5d86784` after verified V5.6.9 merge.

## Identified failure path

Opening-balance **rollback** was made atomic in V5.6.7 and proved against disposable PostgreSQL in V5.6.8, but **commit** still called `OpeningBalancesService.apply()` first (committing an immutable, POSTED ledger journal), then ran a **different transaction** to write `MigrationBatchRow.targetId` and mark `MigrationBatch` COMMITTED. If the batch update failed or the API crashed between transactions, financial history could remain posted while the migration batch remained READY and unlinked. Subsequent retries would depend on separate idempotency recovery, without a single atomic transition.

## Change and compatibility

- Refactor `OpeningBalancesService.apply()` to retain its existing public controller contract and its own transaction/error normalization, delegating the original SQL to `applyWithinTransaction(tx, ...)`. No public API or journal semantics change.
- `MigrationOpeningBalanceCommitService.commit()` now begins one Prisma transaction, obtains the batch advisory and row locks, validates the current batch and all original rows, builds the normalized finance input within that transaction, invokes `applyWithinTransaction(tx, ...)`, and writes row linkage and committed batch state **within the same transaction**.
- Count updated rows exactly, verify a status transition actually returned a row, and reject incomplete/stale COMMITTED replay evidence. A valid already-COMMITTED batch is returned idempotently only when its linked journal is POSTED and tied to exactly the same batch source ID and society.
- Existing rollback behavior, public controllers, finance SQL semantics, and historical journal immutability are preserved.

## Adversarial database proof

`services/api/src/migration/v5.6.10-opening-balance-commit.postgres.spec.ts` creates a randomly identified society, ledger accounts, OPEN accounting period and READY opening-balance batch with two balanced migration rows on the same **disposable** PostgreSQL schema. It injects an error during the *final* batch status UPDATE after actual journal posting SQL has run inside the transaction and verifies **no** journal, row linkage or status transition persists. Then it retries normally and twice checks one posted journal, two linked rows and successful idempotent replay. It does not run outside `GITHUB_ACTIONS=true` on the exact local `aaraagate_ci` database.
