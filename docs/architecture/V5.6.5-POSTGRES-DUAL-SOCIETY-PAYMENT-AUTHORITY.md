# V5.6.5 — Shared-tenant payment authority isolation (nonproduction)

Baseline: `develop` `82c1b75740eb20f27dd2fb40169582e7b273fff4`. V5.6.4 PR #1383 completed protected validation and was automatically merged.

## Gap addressed

The actual migrated-PostgreSQL suite already confirms (a) gate notifications remain society/unit-scoped for a shared tenant in two societies, (b) owner/tenant payment authority, (c) existing-order replay denial after single-society revocation, and (d) independent cross-society invoice rejection. V5.6.5 combines these important rights in one **dual-society tenant** scenario, explicitly exercising the same payment idempotency key on both legitimately accessible society contexts and revoking only the second society's occupancy.

The additional test in `services/api/src/billing/payment-integrity.postgres.spec.ts` uses disposable PostgreSQL, an additional temporary second-society occupancy, randomly generated invoice IDs and one shared test idempotency key. It verifies:

- The same tenant may create independent, uniquely identified orders in two societies with the same idempotency key; both orders must remain tied to the correct society and invoice.
- Even when that tenant legitimately belongs to both societies, an invoice identifier cannot be replayed under the *wrong* society.
- Ending the tenant's second-society occupancy prevents recovering that society's former order (even with the same key), while the first society's legitimate retry still recovers its original order.
- No duplicate order or payment-event audit record is created by unauthorized or repeated attempts.
- The temporary occupancy is deleted in `finally` and the enclosing existing test fixture handles the randomized invoice/order/audit cleanup.

This tests the real `PaymentOrderService` with migrated database access rules and real SQL transaction/idempotency controls. It is not a payment gateway capture or webhook test, full partner RBAC verification, signed package readiness, or production deployment. No service implementation changes, schema migrations, API contract changes, CI workflow changes or productionization.
