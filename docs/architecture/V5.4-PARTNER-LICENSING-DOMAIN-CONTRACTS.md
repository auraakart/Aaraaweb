**Milestone baseline:** V5.3 non-production engineering closure, `develop` SHA `88ef6dc526a0db9a8a1da8f7fe207be2be5bae9a` after merged PR #1261. V5.4 extends Aaraaweb's existing Prisma Partner/PartnerMembership foundation, NestJS entitlement catalogue, Admin UI and auth boundary; no separate microservice, copied mobile app or rewritten society modules.

## V5.4.1 — Commercial licensing contract before activation

`services/api/src/entitlements/partner-license-contract.ts` provides deterministic, pure functions only:

- `licensePhaseAt`: checks strict UTC input and valid calendar dates. A period begins inclusively and expires at an **exclusive** end instant; optional grace is explicit and exclusive. No grace duration, pricing, auto-renewal or legal meaning is invented.
- `intersectPartnerLicenseFeatures`: calculates the *candidate* intersection of platform safety, partner licence, society subscription and society operational feature allowlists, using the **existing** ProductFeature catalogue. Reject duplicate/unknown values; stable output follows existing enum order. This **never grants** user permissions, replaces FeatureGuard or modifies society data.
- `previewPartnerCapacity`: rejects bad integer inputs and previews whether adding a society fits a stated maximum. It does not reserve capacity, determine partner ownership or prevent concurrent oversubscription. Future implementation must use a scoped transaction, version preconditions and idempotency.

**Non-negotiable cutover gate:** Existing `EntitlementService.current` and Society.productTier/featureOverrides continue as live authority for all legacy societies. The V5.1.0 historical compatibility snapshot remains evidence, not a live grant. No live license resolver or partner portal access until ownership history/transfer rules, audience policy, simulated plan grants, compatibility equality, transactional allocation, and essential gate/SOS grace behavior are reviewed and tested.

Required focused tests: allowlist intersection and unknown-field rejection, legacy tier unchanged, start/end/grace timestamp boundaries, impossible dates, zero/negative/oversubscribed capacity, full existing API tests. The canonical full protected PR gates remain mandatory; no staging/main promotion.

## V5.4.2 — Verified-only hostname candidate contract

Implemented in the existing shared config package (`packages/config/src/partner-domain-contract.mjs`) instead of a new server or partner-specific web fork. A one-line canonical preflight gate runs `scripts/partner-domain-contract.test.mjs` with Node's built-in test runner. The pure contract:

- canonicalizes lowercase/IDNA ASCII DNS hostnames; rejects URL syntax, credentials, paths, query/fragment, explicit ports, wildcard, invalid labels, numeric IPs, and localhost/internal/test/example hosts;
- accepts a caller-owned explicit canonical-host reserve list (no hard-coded assumption about real production domains), including subdomains; refuses unreviewed ownership collisions regardless of pending, expired or revoked status;
- resolves **one exact** verified registry row within a checked UTC verification validity interval, with duplicate/unknown/unverified/expired/invalid rows returning no presentation candidate;
- does not read request headers, forwarding headers, DNS, certificates, cookies, HTTP responses or tenant data. A future HTTP adapter MUST use raw Host and only honor forwarded host when validated against a **configured trusted proxy**. Unknown/custom or forged hosts must fail closed before application/login rendering.

Resolution returns an immutable `{hostname,partnerId,brandId}` *candidate only*, never a permission, entitlement, session or verified proof of DNS control. Future partner-domain records must be unique and versioned; a real DNS TXT verifier with challenge expiry, ownership proof, HTTPS and trusted proxy rules is required **before** any host is activated. No live DNS/provider/production integration, partner portal, payment, SSL issuance or main/staging promotion is performed in this slice.

The registry, trusted HTTP adapter and live license enforcement remain separately gated in V5.4.3–V5.4.7. Existing Aaraagate identities and society-scoped operations are unchanged.


## V5.4.3 — Additive versioned commercial plan and DRAFT-only grant ledger

This slice **extends**, rather than duplicates, the existing Partner/PartnerMembership ownership foundation and NestJS EntitlementsModule. It introduces three typed PostgreSQL/Prisma models without modifying Society, its live entitlement flags or session permissions:

- `PartnerLicensePlanRevision`: versioned immutable plan code, allowlisted ProductFeature JSON, society/domain/distribution capacity limits, actor and timestamp. New revisions require a checked expectedVersion and per-plan transaction lock; old plans and references are never overwritten.
- `PartnerLicenseGrant`: partner-scoped plan-revision reference and strict UTC validity/grace period, idempotency key, actor, version and status. **Only DRAFT grants may exist** in V5.4.3: a database CHECK disallows GRANTED/REVOKED (both reserved for a future separately reviewed transition). Thus even direct DB writes cannot silently activate partner features through this table.
- `PartnerLicenseEvent`: append-only ledger with grant, actor, event type, idempotency key and bounded JSON object. The draft-and-event pair is created in one transaction; failure rolls back both. Database triggers reject UPDATE/DELETE of plan revisions and events. Referential integrity retains actors and referenced plans for traceability.

**Platform Super Admin only:** `GET /platform/license-plans`, `POST /platform/license-plans/revisions`, and `GET/POST /platform/partners/:partnerId/license-drafts` reuse the existing BearerGuard, RolesGuard and SUPER_ADMIN role boundary. No partner role obtains these routes. Only active partners may receive new drafts; no client-supplied actor, status or feature entitlement is honored. The server validates the existing ProductFeature enum, strict UTC dates and bounded capacities. A repeated draft idempotency key returns the same result only for exactly matching actor, plan and period; changed payload fails with conflict.

**Unchanged authority:** Existing EntitlementService.current, FeatureGuard, Society.productTier/featureOverrides and the V5.1.0 historical entitlement snapshot are untouched. These commercial rows are not queried from any gate, SOS, login, billing, notifications, tenant-scoped feature resolver or partner portal. V5.4.5 must add authorized status transitions, audited current-plan checks, atomic capacity reservations, compatibility cutover and essential-operations grace controls *before* any license becomes effective.

**Acceptance:** Prisma validate/generate, PostgreSQL 16 clean migration and DB CHECK/immutable audit negative tests, Super Admin route metadata tests, actor/version/idempotent-draft regressions, full API/Admin/Flutter, tenant-access inventory regeneration and protected CI. An operational database migration is not evidence of production deployment. Rollback is a revert to pre-activation code while retaining additive ledger history; do not drop the new tables after records exist. Staging and main remain untouched.


## V5.4.4 — Read-only PartnerMembership-scoped portfolio and members

Reuses the existing Partner, PartnerMembership, Society and NestJS bearer-session boundaries. Two endpoints are added without a second authorization system:

- `GET /api/v1/partners/:partnerId/portfolio` requires an active PartnerMembership in the **requested** ACTIVE partner with one of OWNER, BRAND_MANAGER or COMMERCIAL_ADMIN. It returns only the partner's display name/ID and up to 50 societies' ID/name/status metadata, with a hasMore signal. No units, residents, finances, gate events or PII may enter the projection.
- `GET /api/v1/partners/:partnerId/members` requires OWNER or COMMERCIAL_ADMIN in that same partner. It lists active membership IDs, partner-role labels and timestamps, **not** user IDs, names, emails, phones or society roles. BRAND_MANAGER and SUPPORT may not enumerate members.

Both use the current BearerGuard session userId; caller-supplied partnerId is a requested selector, never authority. A missing, revoked, foreign or suspended partner/member consistently returns 404 without querying the resource list. Authorization and data projection are performed within a single read transaction. They do **not** use SocietyMembership, grant an AppRole, change gate/finance permissions or reuse the Super Admin license-plan writer for partner members. There is no partner write API, operational support impersonation or cross-society PII endpoint.

Required validation: explicit server reauthorization, foreign-partner and revoked-member negative tests, restricted role matrix, scoped society projection, cache no-store, API inventory regeneration, full protected API/Admin/Flutter gates. Remaining V5.4.5 prerequisite: audited society ownership transfers and transactional license allocation/grace enforcement; production custom domains/TLS are still out of scope.

## V5.4.5.1 — Allocation and legacy cutover simulator (non-activating)

A pure, deterministic `@aaraagate/types/partner-license-allocation` module now rehearses a future partner-license allocation, using the same immutable plan, partner and ownership identifiers defined by V5.1/V5.4.3. This is **not** a DB allocator, a new microservice, a change to `EntitlementService.current`, or an authority for any live society, license, session, gate, SOS, or finance action. It does not read PartnerMembership or convert DRAFT grants.

- The input snapshot carries a partner and immutable plan-revision ID, a capacity, allocation generation, society IDs and idempotency receipts. The requested society must belong to that same partner, match the expected current ownership version and match the allocation generation. Inactive partner/grace/expired licenses do not admit new simulated allocations.
- Each accepted proposal returns a *new* immutable state, one incremented generation and one receipt. Exact-key replays are no-ops; reused keys with changed society/plan/ownership/version are conflicts. A second stale candidate cannot pass the optimistic-generation guard; remaining capacity cannot become negative.
- A separate non-mutating `assessLegacyLicenseCutover` compares historical and current enabled feature sets and reports blockers for unauthorized opt-in, missing audited ownership transfer, unapproved essential operations, changed legacy features, or removal of previously active visitor or SOS capabilities. It never replaces the authoritative existing tier/override resolver.
- Node regression tests cover stale concurrent candidates, exact replay vs conflict, cross-partner ownership, downgrade/capacity exhaustion, status/grace/expiry, feature-drift and essential-operation protections. They run in the existing CI structural validation gate without changing API tenant inventory or generating a new service.
- **Still blocked:** V5.1 ownership-transfer history and approval, a persisted allocation ledger, PostgreSQL scoped SERIALIZABLE/row-lock reservation and unique idempotency, approved commercial plan transitions, any legacy grant conversion, and partner domain activation. V5.4.5 is `IN_PROGRESS`, not closed; the simulator is only an implementation prerequisite.

The slice is deliberately separated from DB activation so no invented commercial policy can suspend a society, revoke resident entitlements or disrupt guard/SOS operations. No staging/main or production integration changes.

## V5.4.5.2 — Fail-closed idempotency replay hardening

The pure simulator now rechecks current partner/owner equality, immutable plan revision, ownership generation, ACTIVE partner/license phase, audited-transfer acknowledgement and explicit commercial approval **before** accepting an existing idempotency receipt. This prevents an old receipt from appearing valid after suspension, transfer, downgrade/grace or approval withdrawal. Existing valid same-key replay still returns a no-op without incrementing the allocation generation. Forged snapshot receipts referencing societies that are not allocated fail closed.

This is defensive contract coverage, **not authoritative revocation enforcement**: all input is supplied by a hypothetical test snapshot. No endpoint, database allocator, grant activation or operational entitlement was added. Completing the V5.1 append-only ownership history and reviewed transfer flow, and real PostgreSQL transactional authorization, remains a blocking dependency before live partner licensing.

The existing EntitlementsModule now offers a platform-only selected-society
`POST /platform/societies/:societyId/license-capacity-reservations`. It reuses the
same live locked SUPER_ADMIN authority as ownership transfer. A real PostgreSQL
reservation locks the society then grant, binds the current owner/version to the
grant, checks ACTIVE partner, DRAFT grant version and UTC allocation period,
compares the caller's expected features to the authoritative current legacy
features, and refuses any plan that would omit an enabled feature. Ownership
versions above one require exact immutable transfer history. Grace/expiry admit
no new reservation and no successful replay.

This is **persisted DRAFT engineering work**, not a GRANTED license. The existing
DRAFT-only CHECK is retained, EntitlementService.current remains authoritative,
and no society feature, gate/SOS policy, session, membership or branding is
changed. The response says `DRAFT_RESERVATION` explicitly. Commercial approval,
audited opt-in conversion, activated allocator lifecycle and domain/portal
activation are still later gates; do not market this as live licensing.

Grant-row serialization plus unique grant/key and grant/society/ownership-version
indexes prevent oversubscription and duplicate receipts. Reauthorization,
current owner, grant period/version and legacy equality precede replay. Inserted
receipts freeze plan, grant version, actor, feature snapshot and owner version;
DB UPDATE/DELETE is forbidden. A draft referenced by a receipt cannot be edited
without a future reviewed lifecycle migration. Database insert checks also
validate current owner, actor role/status, partner, period and capacity, so a
raw SQL insert cannot bypass capacity. Owner changes release the old owner's
counted capacity by comparing current ownership versions, while retaining the
old immutable history. Suspended societies continue occupying capacity until
an audited transfer; suspension cannot be used to overbook the draft.

Acceptance: native concurrent capacity-one allocation, exact replay, revoked
membership, stale ownership, transferred-out capacity, feature drift, raw DB
capacity denial, immutability and downstream rollback tests. Synthetic history
is retained in the disposable CI DB; no live migrations or reservations are
executed. Additive-history rollback retains the tables and returns to preceding
application code; do not erase audit data. No staging/main or production work.

## V5.4.5.4 — Approved licensing authority and explicit legacy conversion

Supersedes the earlier activation blocker **in engineering code only**: the
existing DRAFT grant remains an immutable proposal snapshot. A separate immutable
PartnerLicenseApproval records a different currently authorized platform operator
from the draft creator, source society/ownership version, grant version,
idempotency key, reason and explicit PRESERVE_LEGACY continuity policy. Both
maker/checker require active users and current SUPER_ADMIN memberships in the
selected authorizing society. Approval cannot rewrite the original plan/period.
PostgreSQL denies self-approval and overlapping unrevoked approved license periods
for a partner, serializing on the partner row. Append-only revocation permits an
explicit later replacement while keeping all prior records.

The selected society's SOCIETY_ADMIN or SUPER_ADMIN explicitly records OPT_IN or
WITHDRAW under live locked membership. Each event snapshots current productTier,
raw featureOverrides and effective features, and references the historical V5
compatibility migration when present. Sequence ordering prevents withdrawn or
superseded consent being replayed. A consent event never changes society data.
An approved, currently ACTIVE license and latest matching opt-in authorize an
immutable SocietyLicenseAllocation under SUPER_ADMIN control. The grant and
partner locks serialize capacity; receipt uniqueness binds actor, society,
ownership version and exact consent. Every replay revalidates authorization,
current ownership/history, active partner, approval/revocation, license window,
latest consent and full legacy snapshot equality first.

Actual approved allocations and earlier DRAFT rehearsal reservations are separate
ledgers. DRAFT candidates never become active implicitly. Capacity counts only
current-owner allocations bound to the latest opt-in; withdrawal or audited
transfer releases the counted slot while retaining all old history. Re-enrollment
needs a new explicit opt-in and a new admitted allocation. Suspension continues
counting capacity and cannot be used to overbook. New allocations/replays fail
closed in grace, expiry, withdrawal, revoked approval or changed legacy state.

**Continuity policy:** legacy EntitlementService.current and FeatureGuard remain
unchanged, so already enabled gate/SOS and every other legacy feature are preserved
through commercial expiry/grace/revocation. Commercial conversion is the explicit
approved allocation + immutable legacy snapshot, not an automatic tier downgrade
or new operational permission. Partner roles still never grant society roles.
No synthetic consent, approval, license, reservation or live environment mutation
is performed outside disposable test fixtures. No pricing, renewal duration,
payment processor or production domain policy is invented.

Database insert guards enforce maker/checker, scope/status, frozen grant version,
latest consent, snapshot equality, ownership history, active license period,
plan feature containment and capacity even for direct SQL writes. All new ledgers
are append-only. The frozen 16-feature PostgreSQL snapshot function has an
all-tier/malformed-override parity regression against the existing resolver;
future catalogue changes require a new reviewed migration, not editing history.
Actor/society/partner restrictive FKs retain audit history as previously documented.

Acceptance: independent approval/overlap denial, explicit consent, capacity-one
concurrency, withdrawal/re-enrollment, revocation/essential-operation continuity,
revoked/current actor and foreign-scope negatives, direct SQL integrity denial,
transaction rollback, stale legacy/ownership rejection and catalogue parity.
Next after protected merge: existing Admin control-plane views/actions, authorized
local/test domain candidate inspection, cross-partner/rollback engineering closure.
No hosted migration, productionization or staging/main promotion.
