# V5.4 — Partner Portal Licensing and Domain Contracts

**Milestone baseline:** V5.3 non-production engineering closure, `develop` SHA `88ef6dc526a0db9a8a1da8f7fe207be2be5bae9a` after merged PR #1261. V5.4 extends Aaraaweb's existing Prisma Partner/PartnerMembership foundation, NestJS entitlement catalogue, Admin UI and auth boundary; no separate microservice, copied mobile app or rewritten society modules.

## V5.4.1 — Commercial licensing contract before activation

`services/api/src/entitlements/partner-license-contract.ts` provides deterministic, pure functions only:

- `licensePhaseAt`: checks strict UTC input and valid calendar dates. A period begins inclusively and expires at an **exclusive** end instant; optional grace is explicit and exclusive. No grace duration, pricing, auto-renewal or legal meaning is invented.
- `intersectPartnerLicenseFeatures`: calculates the *candidate* intersection of platform safety, partner licence, society subscription and society operational feature allowlists, using the **existing** ProductFeature catalogue. Reject duplicate/unknown values; stable output follows existing enum order. This **never grants** user permissions, replaces FeatureGuard or modifies society data.
- `previewPartnerCapacity`: rejects bad integer inputs and previews whether adding a society fits a stated maximum. It does not reserve capacity, determine partner ownership or prevent concurrent oversubscription. Future implementation must use a scoped transaction, version preconditions and idempotency.

**Non-negotiable cutover gate:** Existing `EntitlementService.current` and Society.productTier/featureOverrides continue as live authority for all legacy societies. The V5.1.0 historical compatibility snapshot remains evidence, not a live grant. No live license resolver or partner portal access until ownership history/transfer rules, audience policy, simulated plan grants, compatibility equality, transactional allocation, and essential gate/SOS grace behavior are reviewed and tested.

Required focused tests: allowlist intersection and unknown-field rejection, legacy tier unchanged, start/end/grace timestamp boundaries, impossible dates, zero/negative/oversubscribed capacity, full existing API tests. The canonical full protected PR gates remain mandatory; no staging/main promotion.

## V5.4.2 — Verified-only hostname candidate contract

Implemented in the existing shared config package (`packages/config/src/partner-domain-contract.mjs`) instead of a new server or partner-specific web fork. A one-line canonical preflight gate runs `scripts/partner-domain-contract.test.mjs` with Node's built-in test runner. The pure contract:

- canonicalizes lowercase/IDNA ASCII DNS hostnames; rejects URL syntax, credentials, paths, query/fragment, explicit ports, wildcard, invalid labels, numeric IPs, and localhost/internal/test/example hosts;
- accepts a caller-owned explicit canonical-host reserve list (no hard-coded assumption about real production domains), including subdomains; refuses unreviewed ownership collisions regardless of pending, expired or revoked status;
- resolves **one exact** verified registry row within a checked UTC verification validity interval, with duplicate/unknown/unverified/expired/invalid rows returning no presentation candidate;
- does not read request headers, forwarding headers, DNS, certificates, cookies, HTTP responses or tenant data. A future HTTP adapter MUST use raw Host and only honor forwarded host when validated against a **configured trusted proxy**. Unknown/custom or forged hosts must fail closed before application/login rendering.

Resolution returns an immutable `{hostname,partnerId,brandId}` *candidate only*, never a permission, entitlement, session or verified proof of DNS control. Future partner-domain records must be unique and versioned; a real DNS TXT verifier with challenge expiry, ownership proof, HTTPS and trusted proxy rules is required **before** any host is activated. No live DNS/provider/production integration, partner portal, payment, SSL issuance or main/staging promotion is performed in this slice.

The registry, trusted HTTP adapter and live license enforcement remain separately gated in V5.4.3–V5.4.7. Existing Aaraagate identities and society-scoped operations are unchanged.


## V5.4.3 — Additive versioned commercial plan and DRAFT-only grant ledger

This slice **extends**, rather than duplicates, the existing Partner/PartnerMembership ownership foundation and NestJS EntitlementsModule. It introduces three typed PostgreSQL/Prisma models without modifying Society, its live entitlement flags or session permissions:

- `PartnerLicensePlanRevision`: versioned immutable plan code, allowlisted ProductFeature JSON, society/domain/distribution capacity limits, actor and timestamp. New revisions require a checked expectedVersion and per-plan transaction lock; old plans and references are never overwritten.
- `PartnerLicenseGrant`: partner-scoped plan-revision reference and strict UTC validity/grace period, idempotency key, actor, version and status. **Only DRAFT grants may exist** in V5.4.3: a database CHECK disallows GRANTED/REVOKED (both reserved for a future separately reviewed transition). Thus even direct DB writes cannot silently activate partner features through this table.
- `PartnerLicenseEvent`: append-only ledger with grant, actor, event type, idempotency key and bounded JSON object. The draft-and-event pair is created in one transaction; failure rolls back both. Database triggers reject UPDATE/DELETE of plan revisions and events. Referential integrity retains actors and referenced plans for traceability.

**Platform Super Admin only:** `GET /platform/license-plans`, `POST /platform/license-plans/revisions`, and `GET/POST /platform/partners/:partnerId/license-drafts` reuse the existing BearerGuard, RolesGuard and SUPER_ADMIN role boundary. No partner role obtains these routes. Only active partners may receive new drafts; no client-supplied actor, status or feature entitlement is honored. The server validates the existing ProductFeature enum, strict UTC dates and bounded capacities. A repeated draft idempotency key returns the same result only for exactly matching actor, plan and period; changed payload fails with conflict.

**Unchanged authority:** Existing EntitlementService.current, FeatureGuard, Society.productTier/featureOverrides and the V5.1.0 historical entitlement snapshot are untouched. These commercial rows are not queried from any gate, SOS, login, billing, notifications, tenant-scoped feature resolver or partner portal. V5.4.5 must add authorized status transitions, audited current-plan checks, atomic capacity reservations, compatibility cutover and essential-operations grace controls *before* any license becomes effective.

**Acceptance:** Prisma validate/generate, PostgreSQL 16 clean migration and DB CHECK/immutable audit negative tests, Super Admin route metadata tests, actor/version/idempotent-draft regressions, full API/Admin/Flutter, tenant-access inventory regeneration and protected CI. An operational database migration is not evidence of production deployment. Rollback is a revert to pre-activation code while retaining additive ledger history; do not drop the new tables after records exist. Staging and main remain untouched.


## V5.4.4 — Read-only PartnerMembership-scoped portfolio and members

Reuses the existing Partner, PartnerMembership, Society and NestJS bearer-session boundaries. Two endpoints are added without a second authorization system:

- `GET /api/v1/partners/:partnerId/portfolio` requires an active PartnerMembership in the **requested** ACTIVE partner with one of OWNER, BRAND_MANAGER or COMMERCIAL_ADMIN. It returns only the partner's display name/ID and up to 50 societies' ID/name/status metadata, with a hasMore signal. No units, residents, finances, gate events or PII may enter the projection.
- `GET /api/v1/partners/:partnerId/members` requires OWNER or COMMERCIAL_ADMIN in that same partner. It lists active membership IDs, partner-role labels and timestamps, **not** user IDs, names, emails, phones or society roles. BRAND_MANAGER and SUPPORT may not enumerate members.

Both use the current BearerGuard session userId; caller-supplied partnerId is a requested selector, never authority. A missing, revoked, foreign or suspended partner/member consistently returns 404 without querying the resource list. Authorization and data projection are performed within a single read transaction. They do **not** use SocietyMembership, grant an AppRole, change gate/finance permissions or reuse the Super Admin license-plan writer for partner members. There is no partner write API, operational support impersonation or cross-society PII endpoint.

Required validation: explicit server reauthorization, foreign-partner and revoked-member negative tests, restricted role matrix, scoped society projection, cache no-store, API inventory regeneration, full protected API/Admin/Flutter gates. Remaining V5.4.5 prerequisite: audited society ownership transfers and transactional license allocation/grace enforcement; production custom domains/TLS are still out of scope.
