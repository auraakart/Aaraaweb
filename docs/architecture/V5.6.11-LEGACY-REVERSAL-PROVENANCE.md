# V5.6.11 — Validate legacy opening-balance reversal provenance before recovery

Baseline: `develop` `50546b266e4ebdb18bf97a24ce9d1e01e894abcc`, after V5.6.10 PR #1390 passed protected CI and merged.

## Defect and bounded fix

V5.6.7 made financial rollback atomic; V5.6.8–V5.6.10 established actual PostgreSQL commit/rollback tests and per-batch journal provenance. The intentional legacy recovery path in `MigrationOpeningBalanceCommitService.rollback()` still treated *any* already-`REVERSED` journal linked to the batch as adequate evidence to mark its migration batch `ROLLED_BACK`, regardless of **who reversed it, why, or under which entry number**.

If an authorized finance administrator reversed an opening balance independently, a later migration rollback would mark the migration batch rolled back without having performed (or verified) the migration-specific reversal process. This is a financial evidence/traceability weakness, not a cross-tenant exploit claim.

V5.6.11 retains support for pre-V5.6.7 partial migration rollbacks but requires that an already-reversed source journal have one linked, POSTED `JOURNAL_REVERSAL` record bearing the **same society, original source journal, `MIG-RV-<batch>` reversal entry number, and exact migration rollback description**. A normal or unrelated reversal now yields a `ConflictException` *before* mutating batch or row state. The POSTED path still reverses and updates the batch in the same Prisma transaction. Already-`ROLLED_BACK` idempotent return is unchanged.

## Regression evidence

- Unit tests cover acceptance of a genuine legacy migration reversal, with verification that the SQL query binds the expected MIG-RV entry number/description, and rejection of an already reversed journal lacking the required evidence.
- The existing gated disposable-PostgreSQL rollback suite adds a manually reversed independent opening-balance journal with its own otherwise-valid COMMITTED migration batch. It verifies that migration rollback rejects the unrelated reversal while preserving the source REVERSED state, COMMITTED batch, two untouched evidence rows and one original manual reversal.
- Existing successful rollback/fault-injection/idempotency and cross-batch isolation cases continue to run. No new CI workflow or extra redundant full-suite dispatch is required.

## Boundaries

This strengthens historical reversal provenance, not a cryptographic attestation or independent device/UAT evidence. Existing journal immutable DB triggers provide the underlying write integrity but admins who can legitimately create accounting reversals still require authorization and segregation-of-duties review. The unchanged test guard permits PostgreSQL integration only in GitHub Actions against an exact local disposable `aaraagate_ci` database.

No schema migration, controller/API change, Android build, hosted payments, productionization, staging/main promotion or third-party integrations. Refresh the generated V5 tenant-access inventory **exactly as reported by CI**; never ignore or bypass that gate.
