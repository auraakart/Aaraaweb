# V5.6.9 — Exact source-batch provenance for finance rollback (nonproduction)

Baseline: `develop` `d572d742d66acbc5aebbf4cf588fc0116ae9e94e` after V5.6.8 PR #1388 passed protected CI and merged.

## Defect

`MigrationOpeningBalanceCommitService.rollback()` validates the society, a single target journal ID, the journal's `sourceType='OPENING_BALANCE'`, and complete row evidence. It previously **did not verify the journal's `sourceId` matched this particular `MigrationBatch.id`**. Thus, a stale or manipulated migration batch with apparently complete target rows could try to reverse an unrelated opening-balance journal *within the same society*. That is an integrity/provenance gap despite the V5.6.7 atomic transaction guarantee.

## Narrow correction

The locked journal lookup now also requires `JournalEntry.sourceId = 'migration:' + batchId`, matching the existing `buildOpeningBalanceInput()` and `OpeningBalancesService.apply()` source identifier contract. A journal belonging to a different batch returns the established not-found error **before** any reversal or batch state change. Correct batch/journal pairs are unchanged, as are the atomic rollback transaction, idempotent second replay and preserved legacy `REVERSED` catch-up.

The existing *real disposable PostgreSQL* suite `v5.6.8-opening-balance-rollback.postgres.spec.ts` now also seeds a second, internally consistent-looking COMMITTED opening-balance batch with two rows pointing to the first batch's journal. It asserts that the second batch cannot roll back the first journal, the first journal remains POSTED and both batches retain their original rollback evidence. The original rollback fault/retry test then executes for the correctly bound first batch.

This is a targeted defense-in-depth code fix and database regression, not a live migration drill or a claim of release readiness. No database schema, CI workflow YAML, Android code, API route contract, external provider, staging/main or productionization changes. The existing source-scanned tenant-access inventory is retained as a CI gate; if source digest changes, commit the **exact regenerated** inventory, not a forged security finding. V5.6 remains PLANNED while V5.4/5.5 external prerequisites and independent TEST runner/Partner A/B acceptance remain blocked at issue #1380.
