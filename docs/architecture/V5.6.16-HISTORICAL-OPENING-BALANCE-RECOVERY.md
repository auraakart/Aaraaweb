# V5.6.16 — Historical opening-balance orphan recovery evidence

**Verified baseline:** `develop` `fc4ae7bff53ba09bfa0b98b87bdfedab4fcfa747` (V5.6.15, PR #1396). This is a **nonproduction test and progress-reconciliation slice** targeting `develop` only.

## Why this matters

Issue #1387 describes the historical split-transaction crash window: `OpeningBalancesService.apply()` could successfully post the immutable journal while its `MigrationBatch` remained READY and its rows unlinked. V5.6.10 (#1390) changed *new* commits to use one transaction. Existing `applyWithinTransaction()` also recognizes a previously posted, same-society/source opening-balance journal if the journal remains POSTED and the stored SHA-256 canonical input digest matches the new normalized input. The READY batch still must have exactly `totalRows` valid, unlinked rows.

## Regression added

The existing real disposable-PostgreSQL suite `services/api/src/migration/v5.6.10-opening-balance-commit.postgres.spec.ts` now exercises a historical orphan explicitly:

1. Create an independent READY opening-balance migration batch containing two balanced normalized rows.
2. Post the opening-balance journal via the *old public* `OpeningBalancesService.apply()` pathway, deliberately leaving migration rows unlinked and batch READY.
3. Call the migration commit with the same society/batch and amount: verify the journal ID is reused; batch transitions to COMMITTED; both rows link; and a further retry returns the same ID. One—and only one—journal remains.
4. In a separate batch, deliberately post an orphan journal with a different amount/content hash. Verify the migration refuses recovery and the batch remains READY with no row linkage or duplicate journal.

The existing V5.6.15 real-database regression independently exercises the same global actor with two societies; V5.6.11–14 assert reversal provenance, exact row counts, target type, concurrent idempotence and stable journal receipts.
