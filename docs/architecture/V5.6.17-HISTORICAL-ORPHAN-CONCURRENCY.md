# V5.6.17 — Concurrent retry of stranded historical opening-balance journals

Baseline: develop `bb848e935133f917b1ee6b474d7fe3b1f99af0a8` after verified successful V5.6.16 PR #1397 and protected CI run #38924094484.

## Purpose

Historical two-phase migration commits could leave a POSTED opening-balance journal attached to a READY migration batch with zero linked rows. V5.6.16 demonstrates deterministic single-request recovery and immutable-content mismatch rejection. This next narrow slice adds **overlapping-retry proof**: prepare an existing correctly posted journal via the unchanged public accounting pathway, then execute two concurrent migration `commit()` calls against that READY batch. Both must return the same journal ID, one committed batch, two linked rows, and exactly one ledger journal.

The new assertion is appended to the existing guarded disposable PostgreSQL test suite. No new CI matrix, external service, runtime API/schema change or database migration is needed. This test does not prove remote worker or device acceptance.

## Unresolved issue #1387 consideration

The existing historical recovery checks canonical content hash, society, batch source ID, row counts, accounting period resolution and the immutable posted journal state. A *separate* potential improvement is explicit matching of batch-creator to original journal-creator/posted-by and line-level provenance on already-posted historical adoption. That requires a runtime SQL-source modification and a freshly regenerated full deterministic V5 tenant-access inventory. This slice intentionally **does not weaken, fabricate or bypass** the inventory checker. Keep issue #1387 open until that review can be performed with full repository-local generation and verified CI evidence.
