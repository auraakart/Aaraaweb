## Why this slice exists

Issue #1387 requires testing historical opening-balance journal recovery, including protected accounting-period transitions. V5.6.16 and V5.6.17 already proved reuse of a matching older POSTED journal, rejection of content-hash conflicts, concurrent retries, one-journal-only semantics, and society scoping. The remaining closed-period interaction needed an explicit real-database negative test, rather than an inference from implementation.

## Implementation and evidence

Extend the *existing* disposable PostgreSQL `services/api/src/migration/v5.6.10-opening-balance-commit.postgres.spec.ts` suite with one test and no other code changes:

1. Create a new disposable society, isolated OPEN accounting period, ledger accounts, READY opening-balance batch and two balanced rows.
2. Post the source journal with the unchanged `OpeningBalancesService.apply()`, simulating the historical two-transaction crash window where the journal is POSTED but the migration batch is READY/unlinked.
3. Close the accounting period with the actor/time evidence required by the persisted schema.
4. Attempt a recovery commit using the unchanged `MigrationOpeningBalanceCommitService.commit()` service. It must reject because the entry date does **not** resolve to exactly one OPEN period.
5. Verify the original posted journal remains POSTED and unique, period remains CLOSED, batch stays READY and no row linkage appears.

The suite preserves its `GITHUB_ACTIONS=true` plus exact `localhost:5432/aaraagate_ci` guard; no test may touch an external/shared ledger. The fixture uses a second society and period so existing success/concurrency tests remain independent. CI must pass the real disposable PostgreSQL job and protected gates before merge.
