# V5.4.23 — Actual Next.js partner SSR and cookie lifecycle behind local TLS 1.3

Baseline: develop e6668769cd478812f998aec8e026d427e53c9288. V5.4.22 PR #1332 and its protected CI completed successfully.

The existing V5.4.18 direct-Host Next.js HTTP regression is preserved. An additional real HTTPS transport acceptance spawns the same actual Next development server and deterministic fixed API double, but reaches the server only through a local TLS 1.3 ingress with a temporary OpenSSL-generated SAN certificate (platform host and two partner hosts). The ingress forwards to a fixed 127.0.0.1 Next port; a supplied Host never selects an upstream. No certificate or private key is stored in git; both are removed after the test.

Acceptance covers canonical TLS Host/SNI matching, invalid SNI rejection, TLS 1.2 refusal, temporary CA enforcement, forwarded-header spoofing rejection **before** Next, HTTPS Origin for mutations, cross-partner cookie copy, actual Next middleware/SSR, authenticated server-side portfolio data, concealment of bearer/refresh tokens, __Host cookie attributes, OTP verification, refresh, logout, rejected app pages, and revoked access.

The Admin protected CI's existing `test:host-ssr` command now executes both direct-Host and HTTPS transport regressions. This changes only test code/commands and does not enable remote reverse-proxy trust in Next. Scoped Admin validation is expected to run; Android compilation remains unchanged.

**Not established:** an independently controlled or remotely authenticated TLS ingress, actual public-browser CA trust, real external provider or hosted API deployment, productionization or Partner A/B Android signing. V5.4 remains IN_PROGRESS until separately provisioned trusted nonproduction ingress is evaluated; staging/main remain untouched.
