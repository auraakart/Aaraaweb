# V5.6.2 — Multi-brand TEST acceptance matrix and rollback readiness

**Baseline:** `develop` `f1f4957393b82d4c3a4fee21600cf26ce709fe74` after V5.5.45 completion/evidence correction. This is a **PREPARATION_ONLY** follow-up to V5.6.1. V5.4 and V5.5 are still IN_PROGRESS; the V5.6 engineering-closure milestone remains PLANNED.

## Purpose and reuse

The existing V5.6.1 preflight (`scripts/check-v4.79.1.4-v5-closure-preflight.mjs`) already proves a conservative nonproduction **blocked closure** and recognizes real base-debug Android regression evidence. This slice **does not replace it** and does not recreate earlier domain/Android/tenant implementation. It adds a *specific, machine-verifiable acceptance checklist* for handoff to infra and UAT teams.

The versioned `v5.6.2-nonproduction-acceptance-matrix.json` records 15 planned cases, stable negative/positive outcome codes, evidence types, and prerequisites. All cases are `NOT_EXECUTED`, all evidence references empty, no candidate SHA has been accepted, and every release/build/branch-promotion flag is false.

`scripts/v5.6.2-acceptance-matrix.mjs` checks all required identities/cases and does **not** allow shortening dependencies, deleting negative isolation checks, forging evidence, changing scope, or representing a planning document as an independent acceptance result. `scripts/v5.6.2-acceptance-matrix.test.mjs` adds one positive test plus 23 fail-closed matrix/manifest mutations. The auto-discovered `scripts/check-v4.79.1.18-v5.6-acceptance-matrix.mjs` runs the Node-only tests in Repository structure, without CI workflow edits, Android jobs, database migrations or runtime network calls.

## Release acceptance order (not yet executed)

1. **Independent test infrastructure** (issue #1380): separately controlled OCI registry, observer and disposable TEST runner. Pin approved image manifest/layer/config digest, source, toolchain and signing identity; verify externally measured process/kernel/readonly mounts and mTLS peer, and atomically consume a single-use challenge. A cryptographically signed self-report or ordinary CI process is insufficient.
2. **Trusted domain ingress**: use an operator-approved TEST hostname and independently checked TLS/mTLS transport to verify exact SNI, certificate/SPKI pin, allowed Host, rejected spoofed forwarding headers, host-only cookies, and session/partner isolation. Prior self-signed loopback test acceptance does not establish this.
3. **Actual Partner A/B TEST Android artifacts**: reuse single Resident/Guard Flutter codebase and approved distribution identities. Generate bounded APK/AABs only after runner authorization. Independently verify fingerprints/signing lineage, package/application ID, versionCode, ABI, manifest, archive digest, provenance and approved source SHA for each Partner A and Partner B role surface. Existing base debug smoke is not partner approval.
4. **Side-by-side install and identity isolation**: with real device evidence, test default Aaraagate, Partner A and Partner B Resident/Guard app coexistence, deep links, Firebase audience separation, account context switching and denied cross-partner operations. No fabricated emulator results.
5. **Database migration and rollback rehearsal**: on disposable PostgreSQL restored from sanitized fixtures, replay additive migrations and legacy historical conversion; reject cross-tenant data, preserve immutable ownership/license/audit records; revert optional brand publication/revision and app deployment without dropping audited data or changing legacy resolver. Attach before/after checked hashes and operator-observed logs.
6. **Risk-weighted V5.6 regression and closure**: full required API/Admin/Flutter/security gates at the exact candidate SHA, society isolation, guard SoD and emergency SOS, occupant gate routing, nonresident owner/tenant billing notice/payer parity, admin host sessions, accessibility and representative performance. Require independently signed acceptance evidence and an explicit release review. `main` always needs owner approval; promotion is *not* part of this slice.

## Matrix evidence semantics

| Prerequisite | Meaning |
| --- | --- |
| `CI` | Required protected workflow and exact SHA |
| `TEST_DB` | Disposable upgraded database with authenticated negative and migration proofs |
| `TRUSTED_INGRESS` | Independently trusted TEST hostname/cert/peer and reverse proxy |
| `INDEPENDENT_RUNNER` | Externally operated and attested isolated TEST OCI execution |
| `PARTNER_ARTIFACTS` | Actual independently signed/inspected approved Partner A/B binaries |
| `TEST_DEVICE` | Physically or independently controlled test-device installation evidence |

The JSON records **required proof kinds**, not supplied or validated proof. These proof kinds cannot be satisfied by mere local fixture JSON, GitHub comments, screenshots of intended output or a CI success unrelated to the exact candidate. Evidence acceptance requires a separately approved future implementation and operator/reviewer signoff. This static checker will intentionally continue to deny release even if somebody edits the milestone statuses to `COMPLETED`.
