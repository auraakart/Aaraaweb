# V5.6.8 — Real PostgreSQL failure-and-retry acceptance for opening-balance rollback

**Baseline:** V5.6.7 PR #1386, merged to `develop` at `0cd274b51a2c25ccac8080b92ee1d96057993206`.

## Why this slice

V5.6.7 made journal reversal and migration-batch status update one Prisma interactive transaction and added mocked-adapter regression tests. Those tests check call ordering and failure propagation but cannot independently prove PostgreSQL actually rolls back previously executed journal INSERT/UPDATE statements when a later batch-status write fails.

V5.6.8 adds one dedicated disposable-PostgreSQL integration regression test, `src/migration/v5.6.8-opening-balance-rollback.postgres.spec.ts`, using actual `AccountingService`, `MigrationOpeningBalanceCommitService`, ledger entries, posting triggers and a COMMITTED migration batch with two evidenced rows.

## Negative and positive acceptance

1. Seed two balanced journal lines and post the opening-balance journal on a randomized test society and accounting period.
2. Create an independently randomized, already-committed `OPENING_BALANCE` migration batch with two rows bound to that journal.
3. Wrap only the TEST Prisma transaction adapter to inject an error *at the final MigrationBatch UPDATE*, after the service has already performed the real journal reversal SQL on the same live DB transaction.
4. Verify that this failed callback leaves the source journal POSTED, the batch COMMITTED, no `rolledBackAt` row timestamps, and **zero persisted reversal journals**.
5. Retry through the normal service; assert that journal is REVERSED, migration batch is ROLLED_BACK, exactly two rows have rollback timestamps and one reversal journal exists.
6. Retry again; assert exact same state with **no duplicate reversal**.

The test is not an accounting migration application test, production reconciliation proof or partner-device UAT. It isolates one finance recovery invariant.

## Isolation and execution

The test intentionally skips unless `GITHUB_ACTIONS=true` and the database URL is specifically a local `postgresql://...@localhost:5432/aaraagate_ci` or `127.0.0.1` equivalent with no schema query parameter. It is discoverable by the existing full API Vitest job; **no added CI workflow or extra runner dispatch** is needed. Immutable journals are deliberately retained until the CI PostgreSQL container is destroyed, matching existing bank/finance acceptance practice. It must not be manually pointed at a developer, staging, shared-test or production database.

No change to runtime services, auth, API, accounting schema or rollout configuration. This slice does not declare V5.6 closure or authorize builds or releases. V5.4 and V5.5 remain IN_PROGRESS; the independent TEST runner and Partner A/B binary acceptance requirement remains [issue #1380](https://github.com/auraakart/Aaraaweb/issues/1380). Changes may enter only `develop` after protected CI gates; `staging` and `main` require separate explicit approval.
