# V5.6.11 — Concurrent opening-balance migration idempotency

**Baseline:** `develop` at `6aa86e1e37d205806ac0b70ccddcd55ea0af90e4`. Prior V5.6.10 integration is green and merged.

## Risk under test

V5.6.7 and V5.6.10 made opening-balance rollback and commit independently atomic on actual PostgreSQL transactions. V5.6.8/9 proved failure recovery and same-batch journal provenance. They did not verify what happens when two legitimate requests arrive **simultaneously** for the same migration batch, causing an advisory-lock race rather than an ordinary sequential retry.

## Evidence

The existing disposable PostgreSQL test fixture is extended with a separately randomized READY opening-balance batch and two balanced ledger rows. Two `MigrationOpeningBalanceCommitService.commit()` calls run concurrently using `Promise.all`; both must resolve to the COMMITTED result while PostgreSQL contains exactly one source journal, two journal lines and two linked evidence rows. Two simultaneous `rollback()` calls must both resolve ROLLED_BACK while exactly one reversal journal exists and both migration evidence rows are timestamped.

The test uses the **real** AccountingService rather than a mock to inspect journal reversal SQL and avoids altering production service code. Existing fault-injection/retry acceptance remains intact in the same test file, executed by the existing protected full API Vitest suite. This does not introduce extra CI workflows, database migrations, runtime APIs, external integrations or additional long test commands. It is gated to `GITHUB_ACTIONS=true` and the isolated local `aaraagate_ci` PostgreSQL database; never use it with shared or production data.
