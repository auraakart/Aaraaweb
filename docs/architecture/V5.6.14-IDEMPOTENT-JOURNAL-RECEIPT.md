# V5.6.14 — Idempotent opening-balance journal receipt

**Verified baseline:** `develop` at `fa97a4f038c7dfd22032232118571173c101dc97` after V5.6.13 (#1394) merged.

## Verified API contract discrepancy

The first `MigrationOpeningBalanceCommitService.commit()` call returned the updated COMMITTED migration batch along with a `journalId` receipt and opening-balance details. Once a batch was already COMMITTED, the service validated that all recorded rows were tied to a POSTED opening-balance journal from the same batch and society, but returned only a `FinanceBatch` object containing its id/status/totalRows. After a successful commit with a lost HTTP response, a retry could succeed without returning the journal identifier clients need to display and reconcile the accounting entry.

## Narrow correction

Only the successful, fully validated COMMITTED replay branch changes: it now returns `{...batch, journalId: ids[0]}`, the same authoritative journal identifier reported on the first successful commit. The existing fail-closed checks for complete evidence, exact source batch/society, correct target type and POSTED status are not relaxed. No extra database reads, schema migrations or public API routes are added. The initial response continues to include its richer `openingBalance` details; this slice guarantees **stable journal identity**, not byte-for-byte response equality.

Existing real disposable-PostgreSQL tests now assert that a sequential retry returns exactly the initial `journalId`, and that simultaneous commits each return the same one persisted journal identifier with no duplicate journal posting. The previously green concurrency and rollback checks remain intact.
