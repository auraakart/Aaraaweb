# V5.6.15 — Dual-society opening-balance migration isolation

**Verified baseline:** `develop` `1abce1eee619759d579e757dd716cb1eaea1ec99`, after V5.6.14 merged.

## Why this slice exists

V5.6.7–V5.6.14 addressed rollback atomicity, journal provenance, evidence integrity, concurrent idempotence and journal receipts. The real disposable-PostgreSQL migration suite still exercised one society at a time. A shared global user can act in multiple societies, so the migration service must always scope its batch and journal operations to the selected society even when a caller supplies a valid batch UUID from a different society.

## Exact acceptance evidence

The existing `v5.6.10-opening-balance-commit.postgres.spec.ts` fixture now introduces a **second society**, separate ledger accounts, financial period and READY opening-balance migration batch, with the **same global actor** used in society A.

- Try to commit society B's batch using society A's `societyId`, and society A's batch using society B's `societyId`; both must fail before applying a journal.
- Try the same swapped-society rollback requests; both must fail without reversing journals.
- Commit B legitimately: the journal must be POSTED under B's society ID with the exact independent amount.
- Roll back B legitimately and prove B has exactly one reversal.
- Confirm A's separately committed batch and POSTED journal remain intact and unchanged throughout B's rollback.

The service already uses scoped `loadBatchForUpdate` and society-bound journal predicates. This regression is **evidence of the existing isolation invariant**, not a new runtime permission or route implementation. Upstream controller authorization remains separately enforced and is not replaced by this service-level check.
