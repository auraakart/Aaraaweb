# V5.14.35 — SOS responder alert fan-out

**Status:** Implementation branch; protected CI pending
**Target:** `develop` only
**Base:** `f028b7b5325d130267479ba0c1ca0cf76c703251`
**Scope:** Non-production source hardening. No staging/main promotion.

## Problem

SOS incident creation currently persists the incident and append-only trigger event, but does not notify eligible responders through the existing resident realtime/push delivery path. Routing policies already select a responder by severity, and the notification system already provides resident-scoped realtime delivery, a durable push outbox, deduplication and retry behavior.

## Changes

- Emit a typed `SOS_INCIDENT_ALERT` event only after a newly created incident commits.
- Resolve the current eligible responder set through the existing `SOS_RESPOND` candidate filter.
- Prefer the active severity-specific policy responder only when that user remains an eligible active responder; otherwise fan out to the current eligible responder set.
- Route events through existing resident realtime and push-outbox delivery, with incident/user deduplication and no new provider integration.
- Do not send a second alert when an idempotent trigger reuses an existing active incident.
- Keep alert copy free of resident names, phone numbers, message text or precise location.

## Compatibility and boundaries

No schema, migration, endpoint, permission, role or mobile contract changes. Existing incident idempotency, advisory lock, tenant transaction, responder permission checks and API response shape are preserved. This does not implement SMS/WhatsApp, external escalation contacts, automatic acknowledgement timers, productionization, physical-device testing, RLS activation or staging/main promotion.

## Acceptance

Protected CI must pass focused SOS/notification tests, API lint/typecheck/build/regression, tenant/security contracts and all required merge gates on the exact PR head. Validate the generated tenant-access inventory through canonical CI.
