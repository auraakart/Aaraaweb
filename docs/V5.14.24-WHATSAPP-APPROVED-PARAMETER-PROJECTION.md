# V5.14.24 — WhatsApp approved-parameter projection

Baseline: V5.14.23 accepted on `develop` at `220e3721bdde5996f859368ae9046b8d7c858a27`.

## Defect and containment
The WhatsApp template dispatcher validates that every required placeholder is present and owned by the event parameter object, but previously forwarded the entire caller-supplied `parameters` map to the provider. Extra fields (such as society identifiers, private contact fields, internal access tokens, or other metadata) could therefore cross the external messaging boundary even when not part of an approved template. The approved registry currently declares only required placeholders and no optional placeholders.

## Change
Construct a fresh outbound parameter map from exactly `approved.requiredParameters` after the existing own-property, nonblank string validation. Reject missing or malformed required placeholders as before, preserving established bad-request errors. Do not mutate the event input, trim or transform accepted placeholder values, or change recipient, language, idempotency, authenticated app paths, template names, or provider implementations.

## Regression evidence
Add per-template regression cases for all three approved WhatsApp templates, checking that incidental sensitive metadata is not passed to the provider and that the input remains intact. Cover inherited metadata alongside owned required parameters. Existing positive dispatch, idempotency and negative validation cases remain.

## Boundaries and acceptance
Only the WhatsApp service, its targeted test and this documentation are changed by the functional patch. Refresh the canonical V5 tenant-access inventory digest after source edits using the repository generator, review the diff, then require protected CI, API test/build/typecheck, tenant-inventory, Flutter, Admin, dependency security and merge gates before merging into `develop`. No live WhatsApp provider, hardware TEST, partner signing, hosted RLS, `staging`, `main`, or production acceptance is claimed.
