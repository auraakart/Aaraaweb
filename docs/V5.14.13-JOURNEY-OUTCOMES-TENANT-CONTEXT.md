# V5.14.13 — Journey and outcomes tenant-local transactions (accepted on develop)

Baseline: accepted V5.14.12 develop `d9c1d2590753d742e76cf9dd62e0caf271b9c893`; canonical tenant-access register records 401 `withTenantContext` calls before this change.

## Bounded runtime change

Four society-filtered journey-funnel SQL aggregates and twelve society-filtered outcomes SQL aggregates use the supplied transaction client's `tx.$queryRaw` within `PrismaService.withTenantContext(societyId, ...)`. The SQL strings, existing explicit `societyId` predicates, date windows, API response contracts, low-level finance permission checks, operational metrics, and privacy controls are retained. Transaction timeouts are 15 seconds for journey and 30 seconds for outcomes; these are safety ceilings rather than target latency values. Concurrency, query plans and pool pressure still require hosted measurement.

Outcomes launches only nine operational queries when `includeFinance=false`: the Receivable financial cohort, outstanding ageing and reconciliation-exception queries are conditional, and finance is returned as `null`. Permission decisions continue to occur at the existing controller boundary. When `includeFinance=true`, all twelve queries run within the same selected society transaction; subqueries for allocations, adjustments and reversals remain joined on both receivable and society identifiers.

**Intentionally global:** `platformPortfolioCommandCentre` and `platformOutcomes` remain unrestricted by a single society transaction and are still protected by platform-only API permission checks. The previously accepted experience-funnel and operations-dashboard conversions are unaffected. This slice does not add hosted RLS policies or change DB grants.

## Accepted regression evidence

- Tests assert no root Prisma client access for journey and outcome reads, correct `societyId` bindings for every statement and no society-context reuse across consecutive requests.
- Finance-on versus finance-off checks prove the three financial database queries are not run for non-finance readers, and preserve existing finance-output redaction.
- Existing PostgreSQL journey fixture verifies inclusive date-window semantics, no cross-society records and query-plan input-row reduction. Its SQL instrumentation captures calls at the real transaction client because Prisma root-method spies do not distinguish transaction proxy delegation. The pre/post window-filter query-plan comparison identifies the appended `AND (` clause independent of SQL indentation; it does not relax aggregate equality or the expected input-row reduction.
- Protected API build/typecheck/test, native PostgreSQL/finance gates, generated tenant register, risk coverage, Admin/Flutter/security and exact tested-head merge all passed before integration into `develop`.

The canonical tenant inventory was regenerated with `node services/api/scripts/tenant-access-inventory.mjs --write` and `node scripts/sync-tenant-access-summary.mjs --write`; the source-derived call-site count increased from 401 to **403**. The temporary branch-local generator workflow was removed before protected PR review and is absent from the merged tree.
