# V5.14.20 — WhatsApp template parameter boundary validation (development candidate)

Baseline: `develop` at `c6924bfc4c5ffe96eb3eaa0e2901e05668ad33e8` after merged V5.14.19 push-token input validation. Scope is limited to the approved WhatsApp-template service and its focused tests.

## Reproduced code defect and remedy

`WhatsAppNotificationService.sendApprovedTemplate` assumed `parameters` was a non-null record with string values because the TypeScript signature said so. Runtime callers supplying an absent/null/array parameter map or a number in a required field could trigger a TypeError instead of the service's established HTTP 400 validation behavior. The missing validation happened before the provider call.

The service now rejects malformed parameter maps and non-string/blank required values with `BadRequestException`. Valid approved templates, required keys, caller parameter payloads, language handling, E.164 recipient validation, idempotency keys and provider routing are unchanged. There is no schema, public endpoint, migration, tenancy, white-label, or infrastructure change.

## Acceptance

Focused regressions cover missing, null and array maps, non-string values and whitespace-only required values; each asserts the provider was not called. Existing positive tests retain valid template send and repeat-key idempotency behavior.

Validate with the repository-pinned Node 22 and pnpm 10:
```sh
pnpm --dir services/api exec vitest run src/notifications/whatsapp-notification.service.spec.ts
pnpm --dir services/api typecheck
```

This is a source candidate, not a claim of passing protected CI or external acceptance. Independent worker, signed Partner A/B artifacts, real devices, hosted RLS/grants and provider integrations remain outside scope under issues #1380 and #212. No staging/main promotion is authorized.
