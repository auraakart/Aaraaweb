## Implementation boundaries and review evidence

The operational overview requires a standard society-authorised session, current PartnerMembership and separate current SocietyMembership permissions per society. Finance/helpdesk additionally respect their existing product features; commercial sessions cannot call it. Figures are read-only outstanding/overdue totals, never an invented collection percentage. Each portfolio is capped at 50 societies in a repeatable-read snapshot.

Complaint evidence is limited to six static, metadata-free PNGs, 1024 pixels and 2 MiB each. Clients normalise camera/gallery images; the server independently validates bytes, scans private storage and rechecks ownership at attachment/read. Signed write URLs and storage keys are never returned to clients. Storage/scanning occur outside database transactions; row/advisory locks protect final quota/idempotency. Exact retries return prior evidence even after closure. An uncertain commit preserves potentially linked objects. Unlinked private objects from process interruption require a production retention/sweeper policy; that operational work stays on hold. Uploads fail closed when storage/scanning is unconfigured.

Asset labels use `AG-ASSET:<society UUID>:<asset UUID>`; the resident can also type an asset code. QR content is a lookup hint, not authority. The API requires current occupancy, same society and a non-retired asset; duplicate case-insensitive codes require the precise QR. Camera/gallery permissions, lost-process behaviour and physical scanning remain unaccepted until device testing resumes.

Commercial terms are bounded provider declarations (invoice issuer, cancellation, refund, settlement, rework), not approved platform policies. A server-recorded immutable request snapshot preserves what was declared at request time; historical unknown terms stay unknown. This is not evidence of payer acceptance or permission to charge. Existing quote approval and all five consolidated-checkout blockers remain in force.
