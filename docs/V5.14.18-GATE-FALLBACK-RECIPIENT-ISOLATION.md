# V5.14.18 — Gate notification fallback recipient isolation (source candidate)

Baseline: V5.14.17 accepted on `develop` at `3ff72ef20ea04e4fd6624adf7a9b95c1bf9e02c0` (PRs #1592 and #1593). This is a bounded source change, **not** a release or production acceptance.

## Defect and scope

The gate fallback path read `User.phone` by globally unique `userId` without rechecking the society/unit recipient relationship, even though the earlier gate-recipient selector was tenant scoped. A stale or misrouted user identifier could therefore read phone data from the global identity catalogue.

The fallback lookup now resolves the phone via `UnitOccupancy` in a `withTenantContext(event.societyId, ...)` transaction. It requires the event unit, matching society and recipient user, active occupancy, active effective dates and enabled gate notifications. A missing unit or unqualified occupant results in existing manual `NO_RESIDENT_PHONE` evidence, not an unrestricted identity retry. Tenant-context failures reject without issuing raw audit SQL. No phone number is written to evidence; only the last four digits may appear for the existing nonproduction IVR simulator.

The existing notification outbox, gate recipient ordering, manual production fallback, push readiness, SQL idempotent evidence upsert, permission contracts and response shape are unchanged. The push evidence write remains independently scoped as before.

## Regression gates

- A qualified resident retains the simulator suffix and scoped persistence.
- No root `User.findUnique` or root raw SQL is permitted.
- A second society with the same input user/unit identifiers obtains only manual evidence when no matching occupancy exists.
- Missing event unit fails closed to manual evidence without reading identity.
- Tenant-context setup failures reject; no global retry or audit write occurs.
- Existing production unconfigured-provider fallback remains manual.
