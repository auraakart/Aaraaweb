## Implemented boundaries

- Android proposal/revision/planner share the native identity validator, with matching new-write SQL constraints. An updated source/config is accepted only against the exact latest independently approved revision; package/namespace/role/signing profile remain fixed. Execution and artifacts remain disabled/unverified.
- Legacy brand-history arrays remain capped at 100 and pin the current publication. Uploaded logos can be cancelled; pending reservations expire after a full 24-hour confirmation grace beyond signed PUT expiry. Cleanup never deletes verified or potentially writable objects. Retention of unused private objects remains an operational task.
- Resident, Guard and Admin logo requests use If-Match against the displayed society/partner revision. A concurrent publication returns 412, avoiding a mixed theme/image. Old image clients remain compatible.
- Partner presentation adds strict name/palette/support settings and an explicit society override allowlist. Partner-private settings never reference society-private logos. Runtime inheritance requires the current partner, approved active grant, current society consent/allocation, ownership version and exact legacy-feature compatibility. Fallback preserves Aaraagate and society presentation; there is no entitlement resolver cutover.
- Society publication records capture publisher, reason, previous publication and verified restore source. Historical publications without such records remain unknown; they are not backfilled with invented actors. Partner publications retain publisher/reason on immutable revisions.
- Partner TEST application identity is independent of a society allocation. Each society proposes its current allocation and obtains independent current platform-operator approval; the same application can have multiple society scopes. Package/signer identity is immutable. Legacy distribution namespaces cannot be silently converted. Distinct applications and legacy distributions share licensed capacity checks.
- Explicit TEST application-session binding narrows a standard authenticated society session, revokes its unrestricted source, and persists the application restriction through bearer checks, refresh and society switching. A package identifier never grants membership. New bindings require current commercial authority; existing operational sessions continue using the unchanged legacy feature/RBAC authority after commercial expiry/withdrawal. Explicit application-scope revocation, role loss and ownership changes still deny the application. Default apps are unchanged.
- Branded clients bind before storing newly issued login/selection sessions. Packaged application identifiers isolate secure-store restoration, and approved package labels are used on login and maintenance CSV headings. Runtime support contacts appear in Profile/Guard tools; Admin document title follows current presentation. Financial record amounts, issuer/society identity and fiscal semantics are unchanged.
- Application push routes use authenticated persisted application scope and an operator-owned application/project/credential-reference registry. Unknown or mismatched projects never use default Firebase. Recipient scope is rechecked at delivery. Invalid/foreign configuration is not an operational delivery success. Credentials and signing keys never enter the database or readiness responses.
- Partner branding/readiness UI distinguishes configured brand/domain/license/scope/push facts from independent worker/device/signing/live-provider acceptance. The society licensing UI owns independent scope approval. Revoked/session-switched UI responses are discarded.

## TEST configuration and external holds

`AARAGATE_ENABLE_TEST_APP_SESSIONS=true` is honored only under NODE_ENV development/test. No setting was activated. Registered application UUIDs can be compiled as `AARAGATE_PARTNER_APPLICATION_ID`; `AARAGATE_APP_DISPLAY_NAME` is presentation only. Trusted package production must bind these values to approved source/config/provenance. V5.9 does not assert that the older society-specific TEST builder produces the new partner-wide identities; actual independent worker integration and artifact/device acceptance remain issue #1380, never a new claim wrapper or a build permit.

Optional `AARAGATE_TEST_PUSH_APPLICATIONS_JSON` maps registered application UUIDs to Firebase project IDs and references named `AARAGATE_TEST_FIREBASE_*` environment variables. Values hold service credentials outside source/database. This is a default-disabled nonproduction path; no live credentials, providers, DNS, signing, distribution or physical devices were configured.
