# V5.14.34 — SOS emergency broadcasts and responder tenant context

**Status:** Implementation branch; protected CI pending
**Target:** `develop` only
**Repository:** `auraakart/Aaraaweb`
**Scope:** Non-production source hardening. No staging/main promotion.

## Problem

`EmergencyBroadcastService` already applies explicit society predicates and snapshots active non-vendor members, but its publish transaction and resident/manage/acknowledgement reads use the root Prisma client rather than the selected society transaction. When a broadcast links an SOS incident, the incident check also runs before the broadcast transaction. `SosRespondersController` similarly reads active responder memberships through the root client.

## Changes

- Establish `withTenantContext(societyId, ...)` for broadcast publication, including linked-incident validation, broadcast insertion, recipient snapshot and recipient readback in one transaction.
- Run resident broadcast listing, management totals and recipient acknowledgement through the selected society transaction.
- Run responder listing through the selected society transaction while retaining the existing SOS_RESPOND guard, role allowlist, active-membership check, active-user check, ordering and API response shape.
- Publish realtime notifications only after the database transaction completes, preserving the existing recipient snapshot and payload.
- Add focused tests proving tenant context is applied and linked-incident validation shares the write transaction.

## Deliberate boundary

`SosFallbackService` first resolves a society from the authenticated user's active occupancy of the requested unit. Because the society is unknown until that narrow lookup completes, the resolver remains a global pre-tenant lookup constrained by user ID, unit ID, active/effective occupancy and active society. The downstream `SosService.trigger` already establishes the resolved society's tenant context. This resolver is intentionally not converted into a tenant transaction without a known tenant.

## Compatibility and exclusions

- No schema, migration, API contract, permission or route changes.
- Existing society SQL predicates, recipient rules, role allowlist and realtime event payloads remain unchanged.
- No PostgreSQL RLS activation, hosted role/grant changes, live providers, physical-device testing, productionization or staging/main promotion.
