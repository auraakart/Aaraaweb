# V4.86.4 — Community circle approval, sender identity and expiry

Resident requests start PENDING and are invisible to other residents until a manager approves them. Rejection includes a reason visible to the requester. Lifecycle reopening cannot bypass request approval. Authorised managers retain direct circle publication.

Joined current society residents or verified owners see each message's sender display name and building/flat label. New messages require a profile name and a current authorised flat relationship. The server resolves these values, prioritising current occupancy over verified ownership and then the most recent relationship. It stores a snapshot with the message, so a later move does not relabel historical posts. Clients cannot supply sender identities. No phone numbers, emails or resident directory are exposed. Legacy messages are backfilled where an author/flat can be resolved; otherwise an explicit unavailable label is shown.

Members can report messages with a reason. Managers have an open/recent report queue and can hide, retain or restore messages, recording their user ID, timestamp and reason. Hidden messages are excluded from resident history. Moderator actions resolve reports transactionally. All operations are society scoped and retain existing NOTICE_READ / NOTICE_MANAGE permissions and NOTICES entitlement.

Managers may set an optional future deletion date/time at creation or later, or clear the date. Resident forms disclose the scheduled deletion date. No date means no automatic deletion. At expiry, the circle stops accepting reads, joins, reports and posts immediately, even before the worker runs. The existing scheduled sweep physically deletes due circles in batches of 100 with row locking; foreign keys cascade to messages, memberships and reports. Default sweep interval is 60 seconds; DISABLE_SCHEDULED_SWEEPS disables physical cleanup, but expiry access checks still apply. Extending/clearing a date is allowed before expiry; expired circles cannot be resurrected through lifecycle controls.

Apply migration `20261008070000_v4864_circle_governance` before deploying the API. Its new fields are additive, preserve existing ACTIVE/CLOSED circles and backfill message identities. Deploy the updated API before the resident client, whose new request list uses an additional endpoint.
