# V5.14.37 — SOS escalation after responder deactivation

## Scope

Ensure an active SOS incident cannot become permanently stranded when its assigned responder's society membership is deactivated or removed before the acknowledgement deadline.

## Finding

The scheduled acknowledgement-deadline sweep selected overdue active SOS incidents only when the assigned responder still had an active `SocietyMembership` row. If that membership became inactive or was deleted after assignment, the incident no longer matched the sweep query. Its acknowledgement deadline could pass indefinitely without the automation recording escalation.

This is an incident-lifecycle defect: the escalation deadline belongs to the incident and must remain enforceable even when the assignee is no longer eligible.

## Change

- Remove the active-membership join from the overdue SOS incident candidate query.
- Continue requiring an active incident, a persisted assigned responder, a non-null acknowledgement deadline that has elapsed, and a null automatic-escalation marker.
- Preserve the existing row lock with `FOR UPDATE OF si SKIP LOCKED`, conditional update, tenant/society join keys on the update, and append-only automation event.
- Add a regression assertion that the SOS escalation query does not depend on current responder membership.

## Behaviour

An overdue incident assigned to a subsequently deactivated/removed responder is still marked auto-escalated and receives its existing `AUTOMATION/ESCALATED` event. This slice does not reassign the incident or dispatch a new notification; those are separate workflow decisions and must not be implied by this state transition.

## Compatibility and validation boundaries

- No API, database schema, permission, role, resident/guard contract, or migration change.
- Existing transaction, cluster lock, row lock, idempotency marker, and audit event semantics remain intact.
- Protected exact-head CI remains authoritative for API, Admin, Flutter, dependency security, tenant inventory, and merge gates.
- No live external providers, physical devices, hardware, productionization, or staging/main promotion.
