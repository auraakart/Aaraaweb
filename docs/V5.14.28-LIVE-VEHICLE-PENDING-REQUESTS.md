# V5.14.28 — Resident live pending vehicle-request visibility

Baseline: `develop` at `0032115bfa5c8bba55e9758fe0d64b63867e11f4` after accepted V5.14.27 PR #1608.

## Root cause and correction

The Resident Vehicles screen showed pending add/removal cards only for the demo repository; real sessions returned an unconditional empty list even though the authorized household API already supplies `accessPreferences.householdChangeRequests` as a server-managed, society/household-scoped mirror. As a result, residents received a confirmation toast but could not see their pending vehicle approval states.

Read the existing mirrored requests from **only the selected household** for live sessions; keep the established demo source. Display only `PENDING` `VEHICLE_ADD` and `VEHICLE_REMOVE` requests. Hide approved, rejected and family-member requests. Preserve original society approval requirements, add/remove mutations, parking data and visual theme. No new endpoint, role, DB query, schema, migration or identity change.

## Acceptance / regression

Extend the existing real-repository Vehicles screen widget fixture to include two pending vehicle records, one approved vehicle request and one unrelated family request. Assert only the two pending vehicle cards are rendered alongside existing registered vehicles and parking labels. Preserve previous compact form and vehicle submission tests.

The canonical indexed `GET /api/v1/household-change-requests/mine` remains available. This slice deliberately uses the currently maintained household mirror to avoid adding a second asynchronous read to the screen; a later independent follow-up can migrate to the indexed endpoint with dedicated recovery/failure tests.

Require protected Flutter analysis/selected/broad widget tests and all repository merge gates before `develop` acceptance. No staging/main promotion, hosted RLS, partner TEST, live provider, signed APK or physical-device acceptance is claimed.
