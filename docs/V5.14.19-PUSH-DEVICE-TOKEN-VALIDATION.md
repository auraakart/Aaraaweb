# V5.14.19 — Push device-token input integrity (development candidate)

Baseline: `develop` at `833eb3c7e8fd97da4b05f2a9d8b5c734aed7a94c` after V5.14.18 source and acceptance-scope clarification. Source work is restricted to push-device registration and unregistration; external TEST, release and hosting gates are unchanged.

## Risk and bounded remedy

Whitespace-only FCM registration tokens passed the service boundary because the values were trimmed after request validation, allowing a blank token to be written or claimed. In the consumer path a blank registration could deactivate a resident token with the same empty key before attempting the consumer insert. The same invalid token could be used in unregister paths.

A shared service-boundary check now rejects tokens that are empty after trimming with a Nest HTTP 400 BadRequestException, before any Prisma read or write. Valid token normalization and owner/society reassignment semantics remain unchanged. The fix applies to resident and independent-home consumer register/unregister operations. No new length or formatting constraints are introduced for legitimate Firebase tokens.

## Regression coverage

Focused unit cases assert each of the four routes rejects whitespace-only values and **does not** execute the DB call or the cross-scope deactivation. Existing tests continue to cover valid-token registration, resident-scoped removal, consumer reassignment and durable push routing. Review the protected CI output before merging this candidate; do not claim local, hosted or physical-device acceptance from source changes alone.

## Release boundaries

No migration, API route, RLS policy, default brand, partner identity, Firebase project or Android artifact behavior is modified. Existing #1380 external operator/partner and #212 hosted-role acceptance remain open. `staging` and `main` must not be automatically promoted.
