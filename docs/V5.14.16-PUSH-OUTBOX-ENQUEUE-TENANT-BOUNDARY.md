# V5.14.16 — Mixed-scope push outbox enqueue tenant boundary (candidate)

Baseline: V5.14.15 accepted on develop af6ca1128856de06e3e375116bb5c861a0fb3f6d; generated inventory previously counted 411 tenant-context calls.

## Bounded change

Resident outbox enqueue now validates a nonempty society and runs its existing parameterized SQL inside `withTenantContext(societyId, tx => ...)`, using only the supplied transaction client's `$queryRaw`. Consumer enqueue requires a null/absent society and keeps the global client. Explicit caller-supplied transaction clients are retained, without creating a second transaction. Unknown target scopes reject before SQL.

The `PushDeliveryOutbox` schema, dedupe keys, ON CONFLICT behavior, mixed resident/consumer global claim/retry processing, delivery envelope checks, Firebase network handling, and global consumer/device-token transfers are unchanged. Claims and retry leases must continue handling work for multiple societies and null-society consumers, so they must not be unconditionally bound to one tenant.

## Regression and acceptance requirements

New unit tests validate sequential society A/B scoped routing, root-client fallback prevention, global consumer routing, explicit transaction propagation, and rejection of invalid target/society combinations without any SQL. The native migrated-PostgreSQL outbox suite now asserts selected-society context on resident enqueue while retaining stale-lease and concurrency tests.

Regenerate the canonical AST inventory and markdown summary via repository scripts. Remove the temporary one-time inventory generation workflow from the PR tree. Require protected full API tests, migrations, restricted-role checks, build, risk coverage, Admin, Flutter, dependency security, and exact tested-HEAD merge.

Hosted RLS/grants, live provider/device validation, productionization, staging, and main remain out of scope.
